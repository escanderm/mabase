# Прототип 02: хранилище, транзакции, хуки

Постановка на разработку. Собрана из `idea.md`, двух ревью Codex
(`idea-review.md` и ответы в чате), `idea-review-2.md` и ревью коллеги.
Общий документ со всеми решениями - `../../design.md`. Всё, о чём
договорились, здесь записано явно, чтобы не искать по переписке.

---

## 1. Зачем этот прототип

Проверить кодом архитектуру ядра до того, как фиксировать её в `idea.md`:

- один общий лог на всю базу, одна строка = одна транзакция;
- снапшот и компактирование, которые переживают падение;
- одна общая очередь записи;
- транзакции, внутри которых видно свои же изменения;
- хуки `before*` / `after*` и вложенные записи из них;
- таймаут, который действительно отменяет транзакцию.

Результат - код, тесты и `RESULTS.md` с явными границами: что проверено,
что нет и почему.

## 2. Что входит и что нет

**Входит:**

- библиотека без HTTP: открыть базу, коллекции, `insert / update / remove /
  findOne / find`, `transaction`;
- обновления `$set`, `$unset`, `$inc`;
- `_id` - ULID (возрастает со временем), генерируется ядром;
- индекс на равенство по одному полю: `Map<value, id[]>`, список **держится
  отсортированным по `_id`** (новые ULID дописываются в конец). Нужен, чтобы
  проверять, что индексы совпадают с данными после восстановления, и чтобы
  заложить порядок для пагинации;
- хуки `beforeCreate / beforeUpdate / beforeDelete` и
  `afterCreate / afterUpdate / afterDelete`;
- точка подписки на коммиты `db.onCommit(fn)` - будущая шина событий;
- лог, снапшот, компактирование, восстановление;
- тесты и тест на падения отдельным процессом.

**Не входит:** HTTP, WebSocket, авторизация, правила доступа, zod-схемы,
файлы, выполнение отложенных задач (сама коллекция `_scheduled` - обычная
коллекция, писать в неё можно), sift и mingo, диапазонные индексы, миграции,
group commit.

**Матчер запросов** - минимальный свой: только равенство по полям, точечная
нотация. Запросы здесь не предмет проверки. sift подключим, когда будет сеть.

## 3. Окружение

- Bun 1.3.x, TypeScript, `bun test`.
- Без внешних зависимостей. Только `node:fs`, `node:path`,
  `node:async_hooks`, `node:child_process`.
- Папка: `prototypes/02-storage/` - `src/`, `test/`, `SPEC.md`, `RESULTS.md`.

## 4. API (по ощущению)

```ts
const db = await openDb({
  dir: './mb_data',
  fsync: true,              // false - только для замеров
  txTimeoutMs: 2000,        // таймаут с момента взятия очереди
  compactAtBytes: 1 << 20,  // порог компактирования лога
  maxDepth: 10,             // глубина вложенных хуков
})

db.collection('rooms', {
  indexes: ['ownerId'],
  hooks: {
    beforeUpdate: async ({ prev, next, db, signal, depth }) => next,
    afterUpdate:  async ({ prev, doc, db }) => { ... },
  },
})

// одиночная операция = транзакция из одной операции
const room = await db.c.rooms.insert({ ownerId: 'u1', participants: [] })
await db.c.rooms.update(room._id, { $inc: { visits: 1 } })

// действие = транзакция из нескольких операций
await db.transaction(async (tx) => {
  const invite = await tx.c.invites.insert({ roomId: room._id, to: 'u2' })
  const found  = await tx.c.invites.findOne({ _id: invite._id })  // видно до коммита
  await tx.c.rooms.update(room._id, { $set: { participants: ['u2'] } })
})

db.onCommit(({ tx, ops, holdMs }) => { /* только после коммита; holdMs - сколько держали очередь */ })

await db.compact()
await db.close()
```

Служебные поля: `_id`, `_createdAt`, `_updatedAt`.

## 5. Транзакции

### 5.1. Одна общая очередь записи

- Любая изменяющая операция (одиночная или `transaction`) - это **корневая
  транзакция**. Она встаёт в одну общую FIFO-очередь.
- Очередь берётся **при первом обращении к базе** внутри транзакции (чтении
  или записи) и держится до применения к памяти. Всё, что транзакция делает
  до первого обращения (например, `fetch`), очередь не держит. Очереди только
  на коммит недостаточно: две операции прочитают одно и то же значение и
  одно увеличение потеряется.
- Для каждой транзакции считается `holdMs` - сколько она держала очередь.
  Отдаётся в `onCommit` и в ошибке таймаута.
- Цена: долгий `before*` или долгое действие задерживает все записи. Для
  нашего масштаба это допустимо.
- Чтения вне транзакции (`db.c.x.find` снаружи) очередь не ждут и видят
  только сохранённое состояние.

### 5.2. Контекст и вложенные записи

- Текущая транзакция передаётся через `AsyncLocalStorage`. Он только носит
  контекст - блокировку держит очередь, а не он.
- Записи изнутри транзакции (из действия и из `before*`-хуков) **входят в
  текущую транзакцию** и попадают в ту же строку лога. В очередь заново не
  встают - иначе транзакция будет ждать сама себя.
- Вложенный `db.transaction(...)` внутри транзакции не создаёт новую, а
  присоединяется к текущей. Точек сохранения (savepoints) нет.
- Каждая вложенная запись увеличивает `depth`. Больше `maxDepth` - ошибка,
  вся транзакция отменяется.
- `before*` вызывается для каждой записи, включая вложенные.

### 5.3. Чтение своих изменений

- У транзакции есть слой поверх памяти (overlay): `Map<коллекция, Map<id,
  документ | удалён>>`.
- `findOne` / `find` внутри транзакции смотрят сначала в overlay, потом в
  сохранённую память. Удалённое в транзакции не находится. Созданное -
  находится. Это касается и поиска по индексу.
- Сохранённую память и индексы транзакция до коммита не трогает.

### 5.4. Порядок коммита

1. Создать транзакцию: `ops`, `overlay`, `state: 'open'`,
   `AbortController`. При первом обращении к базе - взять очередь, запустить
   таймер, запомнить время взятия.
2. Выполнить действие и `before*`-хуки внутри контекста. Каждая запись
   считает новый документ из overlay или памяти, прогоняет `before*`,
   кладёт результат в overlay и в `ops`.
3. Если на любом шаге ошибка - `state: 'aborted'`, overlay выбрасывается,
   очередь освобождается, вызывающий получает ошибку.
4. `state: 'committing'`. Собрать строку лога, дописать в файл, сделать
   fsync.
5. Применить `ops` к памяти и индексам **синхронно**, без `await`. Другие
   операции не увидят половину пакета.
6. `state: 'committed'`. Освободить очередь. Вернуть результат вызывающему.
7. Вызвать `onCommit`-подписчиков.
8. Запустить `after*`-хуки (см. 5.6).

"Запись сохранена" = вызывающий получил результат = строка лога прошла
fsync.

### 5.5. Таймаут

`Promise.race` с таймером **не останавливает** хук: он продолжит работать
после таймаута. Поэтому:

- таймер считает от взятия очереди. По таймеру: `state: 'aborted'`, `abortController.abort()`, очередь
  освобождается, вызывающий получает `TxTimeoutError`;
- любая операция из контекста отменённой транзакции (`insert`, `update`,
  `findOne` и т. д.) бросает `TxAbortedError`;
- коммит отменённой транзакции невозможен - проверка `state` перед шагом 4;
- хуки и действия получают `signal` и могут передать его в `fetch` и другие
  вызовы, которые умеют отменяться.

Поздно завершившийся хук не должен ничего сохранить.

### 5.6. after*-хуки

- Запускаются **после освобождения очереди** и **вне контекста** завершённой
  транзакции (`AsyncLocalStorage.exit` или запуск из чистого контекста).
- Запись из `after*` - новая корневая транзакция, встаёт в очередь как
  обычная. Поэтому `after*` может обновить тот же документ и не зависнуть.
- Ошибка в `after*` пишется в консоль (позже - в `tail`) и не превращает
  сохранённую операцию в "не сохранено".
- `after*` может потеряться при падении между коммитом и запуском. Поэтому
  правило такое:
  - в `after*` - только то, что можно потерять или пересчитать: счётчик
    просмотров, лог, `emit` в сокет;
  - баланс, остаток товара, число использованных приглашений - **в исходной
    транзакции**;
  - письма, вебхуки и другие внешние действия - запись в `_scheduled`
    **внутри транзакции**, выполнение - отдельно (не в этом прототипе).

### 5.7. Ошибка записи на диск

- Перед записью запомнить длину лога.
- Если запись или fsync упали - обрезать лог до запомненной длины,
  транзакцию отменить, память не трогать (её ещё не трогали).
- Если обрезать не получилось - база переходит в режим "только чтение" и
  все записи падают с понятной ошибкой. Дописывать после мусора нельзя.

## 6. Формат на диске

```
mb_data/
  CURRENT              # номер текущего поколения N
  snapshot.<N>.jsonl   # снапшот на момент транзакции N
  log.<N>.jsonl        # транзакции после N
```

### 6.1. Лог

Первая строка - заголовок:

```json
{"format":"mabase-log","version":1,"base":1200}
```

Дальше одна строка на транзакцию. В логе - **итоговые документы**, а не
команды. `$inc` превращается в готовое значение. Так восстановление не
зависит от порядка и не пересчитывает ничего.

```json
{"tx":1201,"ts":1730200000123,"ops":[
  {"op":"put","c":"invites","doc":{"_id":"i1","roomId":"r1","to":"u2","_createdAt":1730200000123,"_updatedAt":1730200000123}},
  {"op":"put","c":"rooms","doc":{"_id":"r1","participants":["u2"]}},
  {"op":"del","c":"tokens","id":"t9"}
]}
```

(В файле - одной строкой, здесь перенос для читаемости.)

- Строка считается целой, только если кончается на `\n` и парсится.
- Номера `tx` идут строго по возрастанию без пропусков.

### 6.2. Снапшот

```
{"format":"mabase-snapshot","version":1,"tx":1200}
{"c":"rooms","doc":{...}}
{"c":"invites","doc":{...}}
{"end":true,"count":2}
```

Нет строки `end` или не сходится `count` - снапшот битый.

### 6.3. Восстановление

1. Прочитать `CURRENT` -> N. Нет `CURRENT` - пустая база.
2. Загрузить `snapshot.N.jsonl`. Битый - отказ запуска с понятной ошибкой.
3. Проиграть `log.N.jsonl`:
   - последняя строка неполная или не парсится - отбросить и обрезать файл;
   - неполная или битая строка **в середине** - отказ запуска с номером
     строки. Молча пропускать нельзя;
   - разрыв в номерах `tx` - отказ запуска.
4. Удалить файлы других поколений и `*.tmp` - это мусор от прерванного
   компактирования.
5. Построить индексы.
6. **Хуки при восстановлении не запускаются.**

### 6.4. Компактирование

Пока держится очередь записи (записи ждут, чтения работают):

1. N = номер последней сохранённой транзакции.
2. Записать `snapshot.N.jsonl.tmp`, fsync, переименовать в
   `snapshot.N.jsonl`, fsync папки.
3. Создать `log.N.jsonl` с заголовком `base: N`, fsync, fsync папки.
4. **Точка переключения:** записать `CURRENT.tmp` с N, fsync, переименовать
   в `CURRENT`, fsync папки.
5. Удалить файлы старого поколения.

Упали до шага 4 - `CURRENT` указывает на старое поколение, его файлы целы.
Упали после - новое поколение уже целое. Мусор убирает восстановление.

Компактирование запускается само, когда лог больше `compactAtBytes`, и
вручную через `db.compact()`.

### 6.5. Точки для имитации падения

Переменная окружения `MB_CRASH_AT=<точка>` - в этой точке процесс убивает
сам себя (`process.kill(process.pid, 'SIGKILL')`):

- `log.beforeWrite`, `log.afterWriteBeforeFsync`, `log.afterFsyncBeforeApply`;
- `compact.afterSnapshotTmp`, `compact.afterSnapshotRename`,
  `compact.afterNewLog`, `compact.afterCurrent`, `compact.beforeDeleteOld`.

`MB_FAIL_WRITE=1` - запись в лог бросает ошибку (для теста 5.7).

## 7. Тесты

Все на `bun test`, без HTTP.

### Транзакции и очередь

1. **Параллельные увеличения.** 100 одновременных `update(id, { $inc: { n: 1 } })`
   -> `n === 100`. То же через 100 одновременных транзакций "прочитать
   `findOne`, записать `$set: n + 1`" -> `n === 100`.
2. **Ошибка в `before*` отменяет всё.** Транзакция создаёт приглашение,
   обновляет комнату, `beforeUpdate` комнаты бросает ошибку. Приглашения нет,
   комната не изменилась, размер лога не изменился. После переоткрытия базы -
   то же самое.
3. **`after*` обновляет тот же документ без зависания.** `afterUpdate`
   увеличивает счётчик того же документа (с защитой от бесконечного цикла).
   Оба изменения сохранены, всё укладывается в 1 секунду.
4. **Таймаут.** `before*` ждёт 2x таймаута, потом пишет. Вызывающий получает
   `TxTimeoutError`. Следующая операция проходит **сразу после таймаута**, не
   дожидаясь хука. Поздняя запись хука получает `TxAbortedError`. Её
   изменений нет ни в памяти, ни в логе, ни после переоткрытия.
5. **Чтение своих изменений.** Внутри транзакции созданное находится через
   `findOne` и через индекс, удалённое - не находится. Параллельное чтение
   снаружи этого не видит до коммита и видит после.
6. **Ошибка в `after*`.** Операция вернула успех, данные сохранены, ошибка
   выведена.
7. **`after*` не присоединяется к сохранённому пакету.** Запись из `after*`
   получает новый номер `tx`.
8. **Глубина.** Цепочка `before*` глубже `maxDepth` -> ошибка, вся
   транзакция отменена.
9. **`onCommit`.** Вызывается только для сохранённых транзакций, строго по
   порядку `tx`. В момент вызова память уже содержит изменения. `holdMs`
   есть и правдоподобен.
9a. **Очередь при первом обращении.** Транзакция A сначала ждёт 500 мс
   (имитация `fetch`), потом пишет. Транзакция B, запущенная сразу после A,
   завершается раньше, чем A начала писать.
9b. **ULID и порядок в индексе.** 10 000 вставок, в том числе параллельных:
   все `_id` уникальны, список id в каждом ключе индекса отсортирован. Тот
   же порядок после переоткрытия базы и после компактирования.

### Диск и восстановление

10. **Ошибка записи** (`MB_FAIL_WRITE`). Транзакция отклонена, память не
    изменилась, лог обрезан до прежней длины, следующая операция работает.
11. **Битая последняя строка** - отброшена, база стартует. **Битая строка в
    середине** - отказ запуска с номером строки.
12. **Компактирование.** После него состояние то же, старые файлы удалены,
    после переоткрытия состояние то же.

### Падения (отдельный процесс)

Рабочий процесс (`test/crash/worker.ts`) в цикле делает транзакции. Каждая
транзакция пишет 3 документа в 2 коллекции с общей меткой `batch`. После
успешного коммита процесс пишет в stdout `ACK <tx> <batch>` синхронно
(`fs.writeSync(1, ...)`), чтобы строка не застряла в буфере.

Порог компактирования маленький, чтобы оно случалось часто.

13. **Каждая точка из 6.5.** Запустить с `MB_CRASH_AT`, дождаться смерти,
    открыть базу и проверить инварианты.
14. **Случайный `kill -9` снаружи.** 50 повторов: запустить, убить через
    случайное время, проверить инварианты, продолжить с той же папкой.

**Инварианты после каждого восстановления:**

- **сохранность:** каждая транзакция, для которой был `ACK`, есть в базе;
- **атомарность:** у каждой метки `batch` либо 3 документа, либо 0;
- для транзакции без `ACK` допустимо любое из двух состояний;
- индексы совпадают с полным перебором данных;
- номера `tx` без разрывов;
- в папке нет мусора от других поколений.

## 8. Замеры для RESULTS.md

- транзакций в секунду, одна за другой, с fsync и без;
- пакетная запись: 100 тыс. документов пачками по 1000 в транзакции, с fsync
  (так будут работать сид и импорт);
- время старта и память (`process.memoryUsage().heapUsed`) для 100 тыс. и
  1 млн небольших документов;
- время компактирования для тех же объёмов.

## 9. Границы проверки (обязательно указать в RESULTS.md)

- `kill -9` проверяет падение **процесса**. Данные в кэше ОС при этом не
  теряются, так что падение питания этим тестом не проверяется.
- На macOS обычный `fsync` не гарантирует запись на физический диск
  (для этого нужен `F_FULLFSYNC`). Указать, на какой ОС шли тесты.
- Group commit не делаем: одна транзакция - один fsync. Замер покажет,
  хватает ли этого.
- Компактирование блокирует запись на всё время. Указать, сколько это
  длится на больших объёмах.
