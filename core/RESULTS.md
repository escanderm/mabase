# Шаг 4: ядро - результаты

Шаг 4 из `design.md` §19: ядро по итогам прототипа 02. Первым делом
`limit`/`sort`/курсор через индекс, дальше коллекции, sift, индексы, схемы,
относительный порог компактирования. Плюс методы коллекции из примера-чата
(Q1).

Bun 1.3.12, macOS arm64 (M4, 16 ГБ), база на внешнем SSD по USB.
2026-10-29.

**Старт на 1 млн зависит от диска, а не от кода.** Одну и ту же базу (248 МБ)
открыл трижды подряд: 2.7 с в первый раз, 0.75 с из кэша ОС. Сразу после
записи было 7.5 и 10.6 с: в те же минуты компактирование тоже замедлилось
с 6.8 до 10.6 с, а его код не менялся. Цифра "6 с" в 02 - это холодное
чтение с USB-диска. Индекс на 1 млн строится за 0.3 с.

**RSS на 1 млн скачет от 1.2 до 1.9 ГБ.** Снапшот читается в память целиком
и режется на строки - пик при старте. Heap стабилен. Потоковое чтение
снапшота уже записано в `design.md` §20.

Индексы почти не добавляют памяти: heap 43 МБ на 100 тыс. - как в 02 без
списка всех `_id`. Список всех `_id` при старте не сортируется, если он уже
по порядку (почти всегда): экономит ~0.3 с на 1 млн.

**Один прогон записи** 100 тыс. документов шёл 10 с вместо 0.7 с (hold
каждой транзакции 4 мс, остальное время - вне кода ядра). Повторить не
удалось ни разу из пяти попыток. Записываю как шум диска или системы.

## Решения, принятые в коде

Это пошло в `design.md` §8:

1. **Без `sort` - порядок по `_id`.** Последний ключ сортировки всегда `_id`
   в направлении первого ключа: при равных значениях порядок стабилен, на
   этом держится курсор.
2. **Каждый документ есть в каждом индексе своей коллекции.** Нет поля или
   пустой массив - ключ null, объект - общий ключ объектов. Поэтому обход
   индекса по порядку видит все документы, и сортировка по полю с индексом
   не теряет документы без этого поля.
3. **Поле-массив (multikey):** диапазон с двумя границами использует только
   нижнюю, остальное проверяет sift. Порядок по индексу такого поля не
   используется - сортировка в памяти.
4. **Вложенные массивы раскрываются, как в sift.** `{ a: 1 }` находит
   `a: [[1, 2]]`. Mongo вложенные массивы не раскрывает. Важнее, чтобы
   индекс и матчер видели одно и то же. Расхождение с Mongo - в README.
5. **Операторы фильтра - белый список:** `$eq $ne $gt $gte $lt $lte $in
   $nin $exists $regex $options $not`, `$and $or`. Всё остальное - ошибка.
   Без него sift выполнил бы `$where` как код.
6. **Сравнение - только со скаляром.** `{ a: { $gt: { x: 1 } } }` - ошибка.
7. **Значения - только то, что переживёт JSON.** `Date`, `NaN`, `Map`,
   классы - ошибка с подсказкой. `undefined` в полях отбрасывается. В памяти
   лежит копия через JSON - ровно то, что прочитается после рестарта.
8. **Схема `z.object` срезает лишние поля** и подставляет умолчания. Нужны
   лишние поля - `z.looseObject`.
9. **Порог предупреждения о большой транзакции - 10 тыс. операций**
   (закрывает вопрос из §20). Пока в консоль, на шаге 8 - в `tail`.
10. **Своё `_id` в индексах** (закрывает вопрос из §20): списки
    отсортированы по строке `_id`. ULID начинаются с цифр, поэтому `general`
    окажется "новее" всех ULID. Для справочных записей это неважно.
11. **`explain(filter, opts)`** - источник кандидатов, сколько проверено,
    сортировалось ли в памяти. Нужен для тестов и для `tail`.

## Что не проверено

- **Типы TypeScript не проверены целиком.** `tsc` запускался без `@types/bun`
  (сеть не дала поставить): видны только ошибки "нет типов Bun/Node", своих
  ошибок в выводе не заметил, но полной проверки не было.
- Порог "выгоднее идти по индексу сортировки" - оценка
  `limit * N / кандидаты < кандидаты`. На случайных данных и в замерах
  работает. На коррелированных данных может ошибаться в скорости (не в
  ответе).
- `count` без индекса на 1 млн не замерял.
- Linux, fsync на Linux - как и раньше, не проверено.

# Шаг 5: действия - результаты

Шаг 5 из `design.md` §19: `defineAction` поверх ядра. 2026-10-29.

## Что сделано

| Файл | Что внутри |
|---|---|
| `src/actions.ts` | `defineAction`, `Actions.run(name, input, user)`, `toClientError`, `onRun` для `tail` |
| `src/errors.ts` | `ActionError(code, message, details?)` и коды -> HTTP |
| `src/db.ts` | `emit` в транзакции: без `after` - событие подписчикам после коммита, с `after` - задача в `_scheduled` в той же строке лога |

Как работает `run`:

1. Нет действия - `not_found`. Нет входа, а действие не `public` - `unauthorized`.
2. `input` проверяется zod. Ошибка - `bad_request` с подробностями по полям.
   Нет схемы `input`, а клиент что-то прислал - тоже `bad_request`.
3. Только потом - транзакция. Неверный запрос очередь записи не занимает.
4. Обработчик получает `{ input, user, db, emit, signal }`. `db.<коллекция>` -
   коллекции внутри транзакции действия.
5. Ответ проверяется на JSON **до коммита**: вернули `Date` - транзакция
   отменяется, клиенту 500.
6. `toClientError`: `ActionError` -> его код и сообщение; всё остальное ->
   500 `internal` без текста, исходная ошибка - в `onError` и `onRun`.

## Решения, принятые в коде

1. **Действие без схемы `input` не принимает входных данных.** Иначе в
   обработчик попадали бы непроверенные данные клиента.
2. **Ответ действия - только JSON.** Проверяется до коммита.
3. **Ошибка схемы коллекции внутри действия - 500**, не 400. Данные клиента
   проверяет `input`; если схема коллекции упала - это ошибка в коде
   действия.
4. **Событие из действия без записей** уходит подписчикам с `tx` последней
   сохранённой транзакции.
5. **`_scheduled`** - системная коллекция с индексами `key` и `runAt`.
   Документ: `{ event, data, runAt, key?, attempts: 0 }`. `key` занят, пока
   задача лежит в `_scheduled`. Доставка, повторы и удаление выполненных -
   шаг 10.
6. **`emit` есть у транзакции** (`tx.emit`, ctx действия). В `before*`-хуках
   пока нет.

- Вызов действий по HTTP и сокету - шаги 7 и 8.
- Таймаут клиенту сейчас - 500 `internal`. Отдельный код (503?) не выбран.

# Шаг 6a: правила, виды полей, фильтры от клиента - результаты

Шаг 6a из `design.md` §19. 2026-10-29.

## Что сделано

| Файл | Что внутри |
|---|---|
| `src/access.ts` | `Access(db, описания, лимиты)`, `forUser(user)` - сессия одного запроса, `c.<коллекция>.find / count / get / insert / update / remove` с правилами и полями, `dependents(c)` для шага 8, `checkClientRegex` |
| `src/db.ts` | `user` в транзакции доходит до хуков (`before*`, `after*`); `maxScanned` у `find`/`count` |
| `src/actions.ts` | действие передаёт `user` в транзакцию - хуки знают, кто пишет |

Через `Access` пойдут HTTP и сокет (шаги 7-8). Хуки и действия работают с
базой напрямую и ограничений не имеют.

## Как работает

- **Нет правила - нет доступа.** Без входа - 401, со входом - 403.
- **`list`/`view` возвращают фильтр** (или `true`/`false`). Он склеивается с
  фильтром клиента через `$and` и идёт в планировщик - индексы работают.
  Чужое по фильтру - пустой список, не ошибка.
- **Одна запись не видна по `view` - 404**, даже если она есть.
- **Запись (`insert`/`update`/`remove`) - одна транзакция** вместе с
  проверкой: правило `view` и `update`/`delete` читают базу в той же
  транзакции. Между проверкой и записью ничего не изменится.
- **`update` получает `before` и `after`** (после применения операторов, до
  хуков).
- **Результат `list`/`view` кэшируется на сессию** (один HTTP-запрос). Запись
  считает правила заново.
- **Поля:**
  - `hidden` - не уходит никогда, клиент не пишет;
  - `private` - видит и пишет только владелец (`owner`); фильтровать и
    сортировать по нему нельзя никому, даже владельцу: фильтр шёл бы по чужим
    записям;
  - `readonly` - клиент не пишет;
  - `immutable` - клиент задаёт при создании;
  - служебные (`_id`, `_createdAt`, `_updatedAt`) - клиент не задаёт.
- **`users` встроенная:** `passwordHash` - hidden; `email`, `phone` - private
  и readonly (меняются через вход); `verified`, `roles` - readonly. Без своих
  правил: каждый видит и правит только себя, создать нельзя (регистрация -
  через вход).
- **Фильтры от клиента:**
  - только по видимым полям (и в `sort`, и в `fields`);
  - `$regex` не длиннее 64, без групп, `|` и обратных ссылок, не больше двух
    `*`/`+`;
  - `limit` по умолчанию 100, максимум 1000;
  - **запрос проверил больше 20 тыс. документов - ошибка 400 "добавьте
    индекс"**. Закрывает вопрос "запрещать фильтры без индекса или
    лимит": лимит на работу, а не на поля. Фильтр без индекса по узкому
    списку (комната по индексу + текст) работает.
- Ошибки ядра из-за запроса клиента - 400 (фильтр, схема с подробностями по

# Шаг 6b: пользователи и вход - результаты

Шаг 6b из `design.md` §19. 2026-10-30.

## Что сделано

| Файл | Что внутри |
|---|---|
| `src/auth.ts` | `Auth(access, опции)`. Для клиента: `register`, `login`, `loginWithPhone`, `refresh`, `logout`, `verify`, `changePassword`. Для сервера: `upsertUser` (сид), `setPassword`, `revokeSessions`. `normalizeEmail`, `normalizePhone` |
| `src/errors.ts` | новые коды: `invalid_credentials` 401, `too_many_requests` 429, `unavailable` 503 |
| `src/access.ts` | `clientErrors` экспортируется: те же 400/404 для ошибок входа |

## Как работает

- **`users`** - обычная коллекция. `Auth` добавляет к схеме приложения
  (`z.object`) зарезервированные поля: `email`, `phone`, `passwordHash`,
  `verified`, `roles`. Своя схема с ними - ошибка при старте. Без схемы -
  `z.looseObject`: любые поля плюс зарезервированные с типами. Индексы
  `email` и `phone` есть всегда.
- **email и телефон уникальны и приводятся к одному виду в хуке `users`**,
  а не в `register`. Хук срабатывает на любую запись: клиент, действие,
  сид, две записи в одной транзакции. Хуки приложения идут первыми, проверка
  MaBase - после них. Удаление пользователя удаляет его сессии в той же
  транзакции.
- **Телефон** - E.164: `89991234567`, `79991234567`, `9991234567` ->
  `+79991234567`; с `+` - как есть, без пробелов, скобок, дефисов.
- **Пароль** - argon2id через `Bun.password`, от 8 до 256 символов.
  **Хэш считается до транзакции**: 65 мс очередь записи не держат.
- **Токены:**
  - access - JWT HS256 на 15 минут, `{ sub, sid, iat, exp }`. `verify`
    проверяет подпись, заголовок целиком (`alg` из токена не читается),
    срок, **что сессия и пользователь ещё есть**. Поэтому выход, смена
    пароля и удаление пользователя действуют сразу, а не через 15 минут. В
    памяти это два поиска по `_id`;
  - refresh - `<id сессии>.<32 случайных байта>`, в `_authTokens` только
    sha256. 30 дней от последнего обновления;
  - **каждое обновление выдаёт новый refresh-токен.** Прошлый токен в
    первые 30 с после обновления - 409 `conflict`: другая вкладка обновилась
    первой, SDK возьмёт новый токен из хранилища. Позже - токен утёк:
    сессия закрывается, новый токен тоже перестаёт работать;
  - истёкшие сессии пользователя удаляются при его следующем входе.
- **Смена пароля** закрывает все сессии пользователя и открывает новую.
  `setPassword` и `upsertUser` с новым паролем закрывают все.
- **Лимит попыток:** 10 неудач за 15 минут на email (или телефон) вместе с
  IP - 429. Попытка считается до проверки пароля: параллельные запросы лимит
  не обходят. Удачный вход сбрасывает счёт. Регистрация - 10 за 15 минут с
  одного IP (если IP известен).
- **Неверный пароль и неизвестный email** - одна ошибка
  `invalid_credentials`. Для неизвестного email хэш всё равно считается
  (на заранее посчитанном хэше той же цены): по времени ответа не понять,
  есть ли такой пользователь. Регистрация на занятый email отвечает 409:
  занятость email видна, как и в PocketBase. Иначе человек не поймёт, почему
  не может зарегистрироваться.
- **Не больше двух хэшей сразу** (`hashConcurrency`). Каждый хэш argon2id -
  64 МБ памяти. Замер: 64 одновременных хэша без ограничения - пик RSS 700
  МБ, процесс с базой в памяти такого не переживёт. С ограничением - 30
  входов в секунду, остальные ждут.
- **authphone.su:** код в формате 6 цифр проверяется до запроса (неверный
  формат до authphone не доходит). Сервер сам вызывает
  `POST https://authphone.su/auth { phoneNumber: '+79991234567', code }` с
  таймаутом 5 с. `{ status: 'ok' }` - вход; 4xx или другой `status` -
  `invalid_credentials`; сеть, таймаут, 5xx, не-JSON - 503 `unavailable`
  (неверным код не считается). Нет пользователя с этим номером - создаётся,
  если `signup` не выключен.
- **`signup: false`** закрывает регистрацию для всех способов. Сервер
  (`upsertUser`, действия) создавать пользователей может.
- **`upsertUser` для сида:** тот же пароль - хэш и сессии не меняются, сид
  можно запускать на каждом старте.

## Замеры

| Что | Результат |
|---|---|
| `Bun.password.hash` argon2id (m=64 МБ, t=2) | 65 мс; `verify` - 56 мс |
| Блокирует ли процесс | нет: хэш в отдельном потоке, таймер каждые 5 мс - пауза до 6.6 мс при 8 хэшах сразу |
| 8 хэшей сразу | 181 мс, RSS 228 МБ |
| 64 хэша сразу | 870 мс, пик RSS 702 МБ - поэтому ограничение 2 |

macOS arm64, 10 ядер.

# Шаг 6c: почта - результаты

| `src/auth.ts` | `requestVerification` / `confirmVerification`, `requestPasswordReset` / `confirmPasswordReset`, `requestEmailChange` / `confirmEmailChange`, `settled()` - дождаться писем в фоне |
| `test/helpers.ts` | поддельный SMTP-сервер на `Bun.listen` и разбор тела письма (quoted-printable, base64) |
| `package.json`, `bun.lock` | nodemailer 10.1.0 |

## Как работает

- **Три режима `Mailer`:** `smtp` (nodemailer), `send` (своя функция, например
  HTTP API Resend), `dev` - нет ни того, ни другого, письмо печатается в
  консоль. `smtp` и `send` вместе - ошибка.
- **Адрес** без переводов строк, запятых, `<>`; **тема** - в одну строку:
  через свою `send` не вставить заголовок `Bcc:`.
- С паролем SMTP без TLS не соединяется (`requireTLS`), таймауты 10 с.
- **С настоящей почтой нужен `appUrl`** - ошибка при старте. В режиме
  разработки без него ссылка - путь `/reset-password?token=...`.
- **Ссылка** - `<id токена>.<32 случайных байта>`, в `_authTokens` -
  sha256, вид, адрес, срок. Одноразовая. Новая ссылка того же вида
  отменяет прошлую. Вид проверяется: ссылка подтверждения не сбрасывает
  пароль. Адрес проверяется: если email пользователя с тех пор сменился,
  ссылки на старый адрес не работают.
- **Письмо - после коммита, вне транзакции.** Не ушло - токен удаляется,
  клиенту 503, можно сразу запросить ещё раз. Одно письмо одного вида - не
  чаще раза в минуту, иначе 429.
- **Сброс пароля** отвечает сразу и одинаково для любого email, письмо
  уходит в фоне, ошибки - в `onError`. Иначе по ответу или по времени было
  бы видно, есть ли пользователь. Новый пароль закрывает все сессии и ставит
  `verified: true` - письмо дошло. Неверная ссылка отвечает 400 до хэша
  пароля: 65 мс на мусор не тратятся.
- **Смена email** требует текущий пароль (если он есть) и свободный адрес.
  Письмо - на новый адрес. После подтверждения: новый email, `verified:
  true`, все сессии и ссылки закрыты. Вошедший по телефону добавляет email
  без пароля.
- Смена пароля любым способом (`changePassword`, `setPassword`, сброс,
  `upsertUser`) гасит отправленные ссылки сброса.

# Шаг 6d: вход через Google и GitHub - результаты

Шаг 6d из `design.md` §19. 2026-10-30.

## Что сделано

|---|---|
| `src/oauth.ts` | описания Google и GitHub `{ authUrl, tokenUrl, scopes, profile() }`, `exchangeCode` |
| `src/auth.ts` | `oauthStart`, `oauthCallback`, `oauthExchange`, `oauthUnlink`; коллекция `_externalAuths { provider, providerId, userId }`; провайдеры в `providers`, ключи в `oauth`, поля нового пользователя - `oauthFields` |

## Как работает

- **Два PKCE.** Сервер держит свой PKCE-ключ для провайдера: код от
  провайдера без него не обменять. SDK присылает `challenge` своего
  `verifier`: одноразовый код из `#` в адресе без `verifier` не обменять.
- **state** - 32 случайных байта, в памяти, 10 минут, одноразовый,
  привязан к провайдеру. Больше 10 тыс. начатых входов - 429.
- **Код для SDK** - в памяти, минута, сгорает после первой попытки, даже
  неудачной. Хранится sha256.
- **Колбэк не бросает исключений.** Он всегда возвращает адрес, куда
  отправить браузер: `appUrl + returnTo + #mb_oauth=...` или
  `#mb_oauth_error=<причина>`. Сбой провайдера - `provider_error`,
  подробности - в `onError`. Таймаут запросов к провайдеру - 10 с.
- **`returnTo`** - только путь (`/...`, не `//...`, без `\`, `#`,
  пробелов): открытого редиректа нет.
- **Кто это** (одна транзакция): привязка есть -> привязать к вошедшему
  -> подтверждённый email есть у пользователя -> новый пользователь.
  - **Захват заранее:** кто-то зарегистрировался паролем на чужой адрес, не
    подтвердив его. Владелец входит через Google с подтверждённым email -
    привязка к этому пользователю, пароль стирается, сессии и ссылки сброса
    закрываются, `verified: true`. У подтверждённого пользователя пароль
    остаётся.
  - **Неподтверждённый email у провайдера** не привязывает к существующему
    (`email_taken`) и не пишется в нового пользователя.
  - **`signup: false`** - нового не создать (`signup_closed`), существующие
    входят.
  - Профиль при повторном входе не переписывается.
- **GitHub:** email - основной из `/user/emails` (в профиле он может быть
  скрыт или не подтверждён); числовой id -> строка; имени нет - `login`.
  Ответ 200 с `{ error }` при обмене кода - ошибка.
- **`oauthFields`** не задают зарезервированные и служебные поля: `roles`,
  `verified`, `email`, `_id` из них отбрасываются.
- Отвязать последний способ входа нельзя. Удаление пользователя удаляет
  его привязки в той же транзакции.

Пути и решения - `design.md` §17. Главное:

- **`/api/c/:collection`**, а не `/api/:collection`: коллекция `files`
  или `auth` столкнулась бы со служебными путями.
- **Без Hono:** обработчик - одна функция, путей мало.
- **Неверный токен - 401 везде**, даже где гостю можно.
- **Таймаут транзакции - 503 `unavailable`.** Остальные неожиданные
  ошибки - 500 без подробностей, в журнал один раз (ошибки действий пишет
  `Actions`, HTTP второй раз не пишет).
- **Тело:** только `application/json` (415), до 1 МБ (413) - считается по
  потоку, `Content-Length` не обязателен.
- **IP клиента:** адрес соединения; `trustProxy` - последний в
  `X-Forwarded-For`.
- **admin:** localhost **и** токен из `mb_data/admin.token` (0600, новый на
  каждый старт). Иначе 404 - не говорим, что admin есть.
- **Секрет:** `MABASE_SECRET` или `mb_data/secret.key` (создаётся сам,
  0600). Вход переживает рестарт.
- **Бэкап:** компактирование под очередью, копия снапшота без очереди,
  новое компактирование ждёт конца копии. Восстановление - открыть папку
  как базу.
- **Импорт:** NDJSON пачками по 1000, существующий `_id` пропускается.
- **Статика:** выход за папку не проходит дважды - по пути и по настоящему
  пути файла (символическая ссылка наружу - 404); SPA-путь без расширения -
  `index.html`.

| `LICENSE`, `CHANGELOG.md` | MIT; что нового в версиях |

## Решения

- **Архив пишем сами, а не системным tar.** На macOS tar добавляет
  `._`-файлы и xattr, GNU tar на Linux потом на них ругается. Свой формат -
  50 строк, его читают и bsdtar, и GNU tar (тест 122, распаковка в Ubuntu).
- **Новый бинарник сначала запускается** с `version`, и только потом
  подменяет старый. Так ловятся чужая архитектура, битая подпись на macOS и

- **Первичная настройка** - email, пароль дважды; после неё токен из

- **Суперпользователи отдельно от `users`.** У приложения свои

- **Первый администратор - только по ссылке из консоли сервера**

  может записать документ, который не прошёл бы схему.
- **Скрытые поля не видит и админка** (`passwordHash`); замена документа

- **Индексы и правила - только просмотр:** конфиг - код в git, правка из

- **Фильтр без `eval`:** свой разбор нестрогого JSON, регулярка
