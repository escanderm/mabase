## Q4. Правило зависит от другой коллекции - подписка не замечает изменений

**Что случилось.** Правило `messages.list` - "сообщения комнат, где я
участник". Участие хранится в `rooms.participants`. Владелец выгоняет Боба
(`kick`): меняется `rooms`, а `messages` не меняется вообще.

`design.md` §12 перепроверяет правило "на старой и новой версии записи" -
но только когда меняется сама запись. Сообщения не менялись, значит у Боба
в открытом чате **остаются и продолжают приходить** сообщения комнаты, из
которой его выгнали. Это та самая утечка "через сокет то, что закрыто по
HTTP", от которой предостерегал ещё `idea.md`.

Это не экзотика: почти любое правило "доступ через членство" так устроено.

**Варианты:**

| | Как | Цена |
|---|---|---|
| А | Правило объявляет зависимости: `dependsOn: ['rooms']`. Когда в `rooms` коммит, сервер заново вычисляет фильтр правила для живых подписок на `messages` у затронутых пользователей. Фильтр изменился - клиенту `reset`, SDK перечитывает выборку тем же механизмом, что при реконнекте | Пересчёт правил на каждый коммит в `rooms`. Комнаты меняются редко - терпимо. Просто в реализации |
| Б | Сервер помнит, какие id отправил каждой подписке, и на изменение зависимости шлёт точные `removed` / `added` (как merge box в Meteor) | Память на каждую подписку, сложнее. Зато клиент не перечитывает |
| В | Денормализация: копировать `participants` в каждое сообщение | Переписывать все сообщения комнаты на каждый `kick`. Плохо |

**Предлагаю А для v1.** `revoked` в клиенте (`feed.on('revoked')`) - это
`reset`, после которого выборка пустая, а правило `view` для комнаты
отказывает. SDK может определить это сам одним запросом.

**Куда:** `design.md` §11 (правила) и §12 (подписки). Решить до шага 8.

## Q5. Кому доставить клиентское событие - считать один раз, а не на каждого

**Что случилось.** `typing` нужно доставить участникам комнаты. Форма
`broadcast: (viewer, data) => boolean` из `design.md` §12 вызывается **для
каждого подключённого клиента**. С `async` и запросом в базу это N запросов
на каждое нажатие клавиши.

**Предлагаю:** считать получателей один раз:

```ts
typing: {
  from: 'client',
  input: z.object({ roomId: z.string() }),
  allow: async (user, data, { db }) => (await roomIdsOf(db, user.id)).includes(data.roomId),
  to: async (data, { db }) => (await db.rooms.findOne({ _id: data.roomId }))!.participants,
}
```

`allow` - может ли отправитель это слать. `to` - список userId. Для
системных событий оставить `broadcast: 'rules'` (по правилам коллекции).

## Q6. Клиентские события - только разрешённые, со схемой, `from` ставит сервер

`design.md` говорит "клиентские события эфемерные, помечены
`origin: 'client'`", но не говорит, **какие** события клиент вообще может
слать. Без списка любой клиент шлёт что угодно и кому угодно.

**Предлагаю:** клиент может слать только события с `from: 'client'` в
конфиге. `input` проверяется zod. Сервер сам добавляет `from: userId` в
конверт - клиентскому полю верить нельзя.

## Q7. Presence - живая выборка по `_presence` вместо отдельного конфига

`design.md` §12: `user.online` с `broadcast: 'authenticated'`. Это
показывает каждому вошедшему пользователю, кто онлайн из **всех** -
включая незнакомых. Для закрытого чата это утечка.

**Предлагаю:** клиент смотрит `mb.live('_presence', {})`, а видимость задаёт
обычное правило `list` на `_presence` (в примере - "только мои контакты").
Одна механика вместо двух. События `user.online` / `user.offline` остаются
для серверных хуков.

## Q2. Поля "видит только владелец"

`design.md` знает `readonly` и `hidden`. `email` пользователя не должен
видеть никто, кроме него самого, - а `hidden` прячет и от него.

**Предлагаю:** третий уровень `fields.private` - видит только владелец
записи. Кто владелец: для `users` - сама запись, для остальных - поле,
указанное в `owner: 'ownerId'`.

## Q3. `readonly` против "задаётся один раз"

`roomId` у сообщения клиент обязан указать при создании, но менять потом
нельзя. `readonly` запрещает и создание тоже.

**Предлагаю:** `fields.immutable` - пишется при создании, потом только
чтение. `readonly` - не пишется клиентом никогда.

## Q1. Чего не хватает в API коллекции

Пример использует методы, которых нет в `design.md`:

| Метод | Зачем |
|---|---|
| `find(filter, { sort, limit, fields })` | `fields` - взять только `_id` для правила, не копируя документы |
| `count(filter)` | сид: "есть ли уже сообщения" |
| `insertMany(docs)` | сид и импорт; сам режет на пачки по 1000 |
| `upsert(filter, doc)` | идемпотентный сид |
| `removeMany(filter)` | удаление комнаты со всеми сообщениями (Q12) |

## Q12. Большие удаления

`deleteRoom` удаляет комнату вместе с сообщениями. В комнате может быть
100 тыс. сообщений - это одна транзакция на 100 тыс. операций: строка лога
~25 МБ и заметное время с занятой очередью записи.

**Варианты:** (а) разрешить - удаление комнаты редкое; (б) `removeMany`
режет на пачки, но тогда удаление не атомарно, и при падении посередине
останется полкомнаты; (в) мягкое удаление: пометить комнату удалённой
атомарно, а сообщения дочищать фоновыми пачками через `_scheduled`.

**Предлагаю (в)**: атомарно и не держит очередь. Нужна поддержка в
правилах: сообщения удалённой комнаты не видны.

## Q8. Действия: кто может вызывать

**Предлагаю:** по умолчанию действие требует входа (`user` в обработчике не
`null`). `public: true` - для действий без входа (например, "сбросить
пароль"). Ограничение частоты вызовов [позже].

## Q9. Ошибки действий и их HTTP-коды

```ts
throw new ActionError('not_found', 'Комната не найдена')
```

| Код | HTTP |
|---|---|
| `bad_request` | 400 (и ошибки zod в `input` - с подробностями) |
| `unauthorized` | 401 |
| `forbidden` | 403 |
| `not_found` | 404 |
| `conflict` | 409 |
| любое другое исключение | 500 без подробностей наружу, подробности - в `tail` |

На клиенте - `MabaseError` с тем же `code`.

## Q10. Своё `_id` в сиде

Сиду нужны постоянные id (`'general'`), чтобы `upsert` находил ту же
запись. Такие id не ULID, и порядок "по `_id` = по времени создания" для них
не работает. Для комнат это неважно, для сообщений - важно.

**Предлагаю:** разрешить своё `_id`, но в документации прямо сказать:
сортировка по `_id` = порядок создания только для сгенерированных id. Для
сообщений в сиде своё `_id` не задавать.

## Q11. Бэкап

`mabase export` есть в CLI, но как он работает на **запущенном** сервере -
не описано. Скопировать `mb_data/db/` во время работы небезопасно, а второй
процесс не откроет базу (LOCK).

**Предлагаю:** `mabase backup <папка>` обращается к запущенному серверу
(локальный admin-эндпоинт). Сервер под очередью записи делает
компактирование и копирует снапшот - это и есть целостный бэкап. На
остановленной базе команда работает напрямую с файлами.

## Мелочи

- **Форма контекста правил.** Пример устоялся на такой:
  `list/view(user, { db })`, `create(user, { doc, db })`,
  `update(user, { before, after, db })`, `delete(user, { before, db })`.
  Значение `false` вместо функции - "всегда нет".
- **Расширение `users`.** `defineCollection('users', ...)` дополняет
  встроенную коллекцию: схема расширяется, правила заменяются. Нужно
  записать явно.
- **Правила с запросом в базу на каждый HTTP-запрос.** `roomIdsOf` - один
  запрос по индексу. Терпимо, но результат стоит кэшировать в пределах
  одного запроса.
- **Имена в SDK:** `live / subscribe / loadMore / close / on('reset')`,
  `mb.c.<коллекция>`, `mb.action(name, input)`, `mb.emit`, `mb.on`,
  `mb.auth.login / restore / user`. Ошибка входа - `invalid_credentials`.

## Что в `design.md` подтвердилось

- **Действия первыми** - работает. Вся логика чата уместилась в 6 действий,
  хуки понадобились только для `authorId` и `editedAt`.
- **Правила-фильтры** - работают для всего, кроме зависимости от другой
  коллекции (Q4).
- **Отложенное событие внутри транзакции** - письмо о приглашении
  получилось простым и надёжным.
- **`live()` с перечитыванием при реконнекте** - клиент вообще не думает о
  сокетах.
