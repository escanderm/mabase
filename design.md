# MaBase - как это будет устроено

> Один бинарник, как PocketBase. Документная база с Mongo-запросами, хуками
> и действиями на TypeScript, авторизацией и встроенным WebSocket. Для своих
> проектов. MIT.

Это общий документ: здесь собраны все решения, которые одобрены после
обсуждения. Он заменяет `idea.md` как источник истины. `idea.md` остаётся
как исходная идея, ревью лежат рядом.

**Источники:** `idea.md`, `idea-review.md` (Codex), `idea-review-2.md`,
ответы Codex в чате, ревью коллеги (сортировка и пагинация, ULID, схема на
записи, пакетная запись, события из `onCommit`, обязательный реконнект,
честный масштаб; второе ревью - lock-файл, папка `mb_data/db/`, потеря
`CURRENT`), прототип `prototypes/01-binary-hooks/`, прототип
`prototypes/02-storage/` (`SPEC.md` и `RESULTS.md`), пример-чат
`examples/chat/` (`API-NOTES.md`, вопросы Q1-Q12).

## 1. Зачем

Я каждый день пользуюсь PocketBase, и мне нравится, как с ним удобно. Но:

- он на Go, и я не понимаю, что у него внутри;
- в нём нет встроенного WebSocket так, как мне хочется;
- SQL мне тяжёл. Модель документов как в Mongo удобнее и универсальнее: она
  подходит и для чата, и для долгого хранения.

Нужен инструмент для своих проектов (пет-проекты, MVP, внутренние
инструменты, мобильные бэкенды), который:

- ставится одним файлом и запускается одной командой, как PocketBase;
- написан на TypeScript целиком, и я понимаю каждую его часть;
- не требует SQL, схем и миграций там, где они не нужны;
- даёт авторизацию, права доступа, файлы и realtime без отдельных сервисов;
- позволяет описать бизнес-логику хуками и действиями;
- превращает каждое изменение данных в **событие**, на которое можно
  повесить обработчик.

Суть: взять лучшее из нескольких систем и собрать очень простой инструмент,
идеальный для своих проектов. Конкурировать с PocketBase не цель.

**Масштаб честно:** бэкенд до сотен тысяч документов на один процесс. Вся
база живёт в памяти. [проверено в 02]

| Документов (~250 байт JSON) | Старт | Heap | RSS |
|---|---|---|---|
| 100 тыс. | 0.15 с | 43 МБ | 225-300 МБ |
| 1 млн | 0.75 с из кэша ОС, 2.7 с с холодного USB-диска | 900 МБ | 1.2-1.9 ГБ |

Старт на 1 млн упирается в чтение 248 МБ с диска, а не в код (замер шага 4;
"6 с" в 02 - холодное чтение). RSS скачет, потому что снапшот читается
целиком - потоковое чтение в §20. Индексы почти не добавляют памяти.

Грубо: **~1 КБ heap и ~1.3 КБ RSS на документ. VPS с 1 ГБ памяти -
примерно 300-400 тыс. документов с запасом.** Эта цифра идёт в README.

Большие файлы и статика - не документы в памяти, а файлы на диске с
записью-описанием в базе (§16). "Универсальная" здесь значит модель данных,
а не объём.

**Отклонённая альтернатива:** WS-мост на Bun рядом с PocketBase дал бы
большую часть пользы за выходные. Отклоняю явно: **я хочу понимать, что
внутри**, и владеть кодом целиком. Если на третьем месяце работы над логом
появится вопрос "зачем" - ответ здесь.

## 2. Принципы

1. **Самое простое из работающего.** Из каждой системы берём одну лучшую идею.
2. **Понимаю всё, что внутри.** Поэтому своё хранилище, а не SQLite и не
   чужой движок.
3. **Сначала библиотека, потом сервер.** Ядро работает без HTTP - из скриптов,
   тестов, сидов. HTTP и сокеты - слой сверху.
4. **Один язык везде.** Ядро, хуки, действия, сиды, миграции, клиент -
   TypeScript.
5. **Один рантайм - Bun.** Без запасного варианта на Node.
6. **События - первоклассная сущность**, а не побочный эффект.
7. **Действия первыми, хуки вторыми.** Бизнес-логика пишется явными
   действиями. Хуки - для проверок и мелких реакций. Иначе через полгода
   проект превратится в "поле изменилось -> хук 3 -> хук 7". В README
   действия идут раньше хуков.
8. **Ограничения принимаем осознанно:** один процесс-писатель, база
   помещается в память, нет распределённости.
9. **Каждое обещание - с контрактом.** Если пишем "сохранено", "заменяет
   очередь задач" или "транзакция" - рядом написано, что именно это
   гарантирует.

## 4. Слои

```
cli          -> serve / seed / migrate / tail / compact / backup / export / import
http         -> REST + WebSocket (Bun)
auth         -> коллекция users, пароль, JWT + refresh
events       -> шина событий, presence, подписки, отложенные события
actions      -> defineAction: явные операции бизнес-логики
hooks        -> before* / after* вокруг записей, on(event)
rules        -> правила доступа: фильтры + проверки
collections  -> схема (zod), find/insert/update/remove, индексы, sift
transactions -> общая очередь записи, overlay, контекст
storage      -> общий лог + снапшот, Map в памяти
```

Каждый слой знает только о нижних. `storage` + `transactions` +
`collections` - ядро, которое не импортирует ничего сверху.

## 5. Рантайм и упаковка [проверено, CLI - в шаге 7b]

Проверено в `prototypes/01-binary-hooks/` (Bun 1.3.12, macOS arm64).

- **Рантайм - Bun.** Он один закрывает три требования: один файл
  (`bun build --compile`), TS без сборки, встроенный WebSocket.
- **Бинарник `mabase`** содержит Bun, zod и весь API. На машине не нужно
  ставить Bun. Старт - 20-30 мс. Размер - около 60 МБ.
- **Хуки и конфиг** - обычные `.ts`-файлы рядом с бинарником. Бинарник
  подгружает их при старте через `import()`.
- **`import { on, z, defineCollection } from 'mabase'`** работает без
  `node_modules`: бинарник отдаёт свой API как виртуальный модуль
  (`Bun.plugin`).
- **zod** берётся из `mabase`. Своя копия zod у пользователя тоже не
  ломает проверки (zod 4).
- **npm-пакеты в хуках** - по желанию. Если рядом есть `node_modules`,
  работают как обычно.
- **Ошибка загрузки хука останавливает запуск.** Сервер не должен работать
  без части бизнес-логики. Необязательный хук помечается явно. [решено]
- **Типы для редактора:** бинарник пишет `mb_data/types.d.ts` и кладёт рядом
  типы zod (около 300 КБ). [решено, не сделано - нужна сборка типов API в
  один файл]
- **CLI** [проверено в шаге 7b]: `mabase serve`, `seed`, `backup <папка>`,
  `import <коллекция> <файл.ndjson>`, `version`. Проект - текущая папка (или
  `--root`), данные - `--dir mb_data`, статика - `mb_public/`, если есть.
  `bun run build` собирает `dist/mabase` и переподписывает его на macOS.
  Бинарник 62 МБ; пример-чат в чистом окружении (`env -i`, Bun не в `PATH`)
  делает сид, отвечает по HTTP и делает бэкап. Старт - 58 мс, первый
  запуск нового бинарника на macOS - 1.3 с.
- **`seed` пишет в базу напрямую - сервер должен быть остановлен** (иначе
  ошибка с подсказкой). `backup` и `import` работают в обоих случаях: база
  свободна - открывают её сами (с конфигом и хуками проекта), занята - идут к
  серверу через `admin.json`.
- **macOS:** Bun собирает файл с битой подписью, система его убивает. В
  сборке после компиляции: `codesign --remove-signature` и `codesign -s -`.
  Для раздачи другим на macOS нужна нормальная подпись. Linux не затронут.

### Структура проекта

```
my-project/
```

## 6. Хранение [проверено в 02]

Проверено в `prototypes/02-storage/`: 36 тестов, включая падение процесса в
8 точках и 50 случайных `kill -9`. Ни одна подтверждённая транзакция не
потерялась, ни один пакет не записан частично.

### Общий лог на всю базу

Не отдельный лог на коллекцию, а **один лог на базу. Одна строка = одна
транзакция.**

```
mb_data/db/
  CURRENT              # номер текущего поколения N
  LOCK                 # pid процесса, который держит базу
  snapshot.<N>.jsonl   # снапшот на момент транзакции N
  log.<N>.jsonl        # транзакции после N
```

```json
{"tx":1201,"ts":1730200000123,"ops":[{"op":"put","c":"invites","doc":{...}},{"op":"put","c":"rooms","doc":{...}},{"op":"del","c":"tokens","id":"t9"}]}
```

- В логе - **итоговые документы**, а не команды. `$inc` превращается в
  готовое значение.
- Номер `tx` идёт по возрастанию без пропусков. Он же - основа для
  `eventId`, `tail` и реконнекта сокета.
- У каждого файла - заголовок с версией формата. У снапшота - строка конца
  с числом документов.
- Данные в памяти: `Map<id, Document>` на коллекцию. Документы в памяти
  заморожены: обновление всегда создаёт новый объект.

### Один писатель - защищён, а не только объявлен

Файл `LOCK` создаётся через `O_EXCL` с pid процесса. Второй процесс на той
же папке получает понятную ошибку **до любой записи**. Без замка два
процесса тихо теряли половину данных, а база выглядела здоровой.

- Замок умершего процесса (`kill -9`) следующий запуск забирает - проверка
  pid.
- Пустой свежий замок считается занятым 2 секунды: его могли только что
  создать.

### "Сохранено" - это что

**Запись сохранена, когда строка лога прошла fsync.** Только после этого
клиент получает ответ и уходят события.

Если запись или fsync упали - лог обрезается до прежней длины, транзакция
отменяется, память не тронута. Не получилось обрезать - база переходит в
режим "только чтение": запись запрещена, чтение работает, после перезапуска
недописанная строка отбрасывается.

Скорость [проверено в 02, macOS, внешний SSD]: ~1700 транзакций/с с fsync
по одной; ~81 000 документов/с пачками по 1000. **Group commit не нужен.**

### Восстановление

1. `CURRENT` -> загрузить снапшот -> проиграть лог.
2. Неполная последняя строка - отбросить **с предупреждением** в консоль
   ("отброшена недописанная транзакция"). Битая строка в середине или разрыв
   в номерах `tx` - отказ запуска с понятной ошибкой.
3. Удалить мусор от прерванного компактирования: старые поколения и свои
   `*.tmp`.
4. **Хуки при восстановлении не запускаются.**

**Когда база отказывается стартовать и ничего не удаляет:**

- нет `CURRENT`, а в файлах базы есть данные. Перезаписываются только пустые
  недописанные файлы прерванного создания новой базы;
- есть поколение **новее** `CURRENT`, и в его логе есть транзакции.
  Например, `CURRENT` восстановили из старого бэкапа.

Восстановление в этих случаях - руками. Молча стереть данные хуже, чем не
запуститься.

### Компактирование

Само - **когда лог стал больше снапшота** (и не меньше 16 МБ), или командой
`mabase compact`. Порог относительный: при фиксированном 1 МБ база в 1 млн
документов переписывала бы 248 МБ снапшота и стояла 6.7 с ради каждого
нового мегабайта. Так работа на компактирование пропорциональна записи.
[решено по замеру 02, проверено в шаге 4: тест 36]

Пока идёт, запись ждёт, чтение работает: 0.9 с на 100 тыс. документов,
6.7 с на 1 млн. Компактирование без остановки записи (снапшот с
замороженного состояния, пока новые транзакции идут в новый лог) [позже].

1. Новый снапшот во временный файл -> fsync -> переименовать.
2. Новый пустой лог -> fsync.
3. **Точка переключения:** атомарно переписать `CURRENT`.
4. Удалить старое поколение.

Упали до шага 3 - живёт старое поколение. После - новое.

### Бэкап [проверено в шаге 7]

`mabase backup <папка>`:

- **сервер запущен** - команда обращается к нему через локальный
  admin-эндпоинт (только с `localhost`). Сервер под очередью записи делает
  компактирование и копирует снапшот в папку. Это целостный бэкап на один
  `tx`. Копировать `mb_data/db/` руками во время работы нельзя, а второй
  процесс базу не откроет (LOCK);
- **сервер остановлен** - команда сама берёт LOCK и копирует файлы
  текущего поколения.

Бэкап - это обычная папка `db/` с одним снапшотом и пустым логом:
восстановить = положить её на место `mb_data/db/`.

Как сделано (`db.backup(папка)`): компактирование под очередью записи,
затем копия снапшота **уже без очереди** - база пишет дальше. Новое
компактирование ждёт конца копии, иначе оно удалило бы копируемый
снапшот. Папка должна быть пустой.

### История

**В первой версии истории нет.** После компактирования старые строки лога
пропадают. Клиент с номером `tx` старше начала лога получает ответ
"перечитай состояние". Аудит и история со сроком хранения - отдельная
функция. [позже]

## 7. Транзакции [проверено в 02]

### Очередь

- **Одна общая очередь записи** на всю базу, FIFO.
- Любая изменяющая операция - **корневая транзакция**. Она берёт очередь
  **при первом обращении к базе** (чтении или записи) и держит её до
  применения к памяти. Очереди только на коммит мало: две операции прочитают
  одно значение, и одно увеличение потеряется.
- Всё, что действие делает **до** первого обращения к базе (например,
  `fetch`), очередь не держит.
- Цена: долгий `before*` или долгое действие задерживает все записи. Поэтому
  таймаут короткий, а `tail` показывает, сколько каждая транзакция держала
  очередь.
- Чтения вне транзакции очередь не ждут и видят только сохранённое.

### Вложенные записи

- Текущая транзакция передаётся через `AsyncLocalStorage`. Он только носит
  контекст, блокировку держит очередь.
- Записи из действия и из `before*`-хуков **входят в текущую транзакцию** и
  попадают в ту же строку лога. Заново в очередь не встают - иначе транзакция
  ждала бы сама себя.
- Вложенный `db.transaction()` присоединяется к текущей. Точек сохранения нет.
- Глубина вложенности ограничена (по умолчанию 10).

### Чтение своих изменений

Внутри транзакции `find` и `findOne` видят её же подготовленные изменения
(overlay): созданное находится, удалённое - нет. Снаружи этого не видно до
коммита.

### Порядок коммита

1. Взять очередь при первом обращении к базе.
2. Выполнить действие и `before*`-хуки. Изменения копятся в overlay.
3. Ошибка на любом шаге - транзакция отменена целиком, вместе со всеми
   вложенными записями. **Ошибка в `before*` отменяет транзакцию, даже если
   код действия её поймал** - транзакция с упавшим хуком никогда не
   сохраняется частично.
4. Дописать строку в лог, fsync.
5. Применить к памяти и индексам **синхронно**, без `await` - никто не
   увидит половину пакета.
6. Освободить очередь, ответить вызывающему.
7. Отправить события.
8. Запустить `after*`.

### Таймаут

По умолчанию **2 секунды** с момента, когда транзакция взяла очередь. Пока
она держит очередь, вся база не пишет, поэтому таймаут короткий.
`Promise.race` хук не останавливает, поэтому:

- по таймауту транзакция помечается отменённой, очередь освобождается,
  вызывающий получает ошибку;
- любое обращение из контекста отменённой транзакции бросает ошибку - поздно
  завершившийся хук ничего не сохранит;
- хук получает `signal` (`AbortSignal`) и может передать его в `fetch`.

**Где делать внешние вызовы (`fetch`, письма, API):**

- в действии **до** первого обращения к базе;
- в `after*`;
- через `_scheduled` (§13).

В `before*` - нельзя: он всегда держит очередь.

### Чего транзакция не умеет

Отменить уже сделанное снаружи. Отправленное письмо назад не вернуть.
Поэтому внешние действия - только после коммита (см. 9 и 12).

## 8. Коллекции, запросы, индексы

- `defineCollection(name, { schema?, indexes?, fields?, owner?, rules?, hooks? })`.
- **Методы коллекции** [решено, пример-чат Q1] - одинаковые на сервере
  (`db.<коллекция>`) и в клиенте (`mb.c.<коллекция>`, там с правилами):

| Метод | Что делает |
|---|---|
| `find(filter, { sort, limit, fields })` | `fields` - взять только нужные поля, например `['_id']` для правила, без копирования документов |
| `findOne(filter)` | первая запись или `null` |
| `count(filter)` | число записей; по индексу - без перебора |
| `insert(doc)` / `insertMany(docs)` | `insertMany` сам режет на пачки по 1000 (§15) |
| `update(id, ops)` | `$set $unset $inc $push $pull` |
| `upsert(filter, doc)` | найти по фильтру и обновить, или создать. Для идемпотентных сидов |
| `remove(id)` / `removeMany(filter)` | `removeMany` - одна транзакция; про большие удаления - §10 |

- **Схема - zod, необязательная.** Даёт валидацию и TS-типы. Нет схемы -
  свободный документ.
- **Схема проверяет только запись, чтение не проверяет.** [решено] Поменял
  схему - старые документы читаются как есть. Удалённое из схемы поле просто
  перестаёт проверяться. Новое обязательное поле: у старых документов его
  нет, хотя TS-тип говорит обратное. Поэтому новое поле делается
  необязательным, либо старые данные правятся миграцией.
- Служебные поля: `_id`, `_createdAt`, `_updatedAt`.
- **`_id` - ULID** [решено]: 26 символов, возрастает со временем.
  Сортировка по `_id` = порядок создания. Своё `_id` можно задать (например,
  `'general'` в сиде, чтобы `upsert` находил ту же запись), но тогда
  порядок создания для этих записей не гарантирован. В документации прямо
  сказать: своё `_id` - для справочных записей (комнаты, настройки), не для
  лент (сообщения). [решено, Q10] Списки индексов отсортированы по строке
  `_id`; ULID начинаются с цифр, поэтому `'general'` окажется "новее" всех
  ULID. Для справочных записей это неважно. [проверено в шаге 4]
- Системные коллекции начинаются с `_`: `_presence`, `_scheduled`,
  `_migrations`, `_refreshTokens`. Часть только в памяти.
- **Запросы** - подмножество Mongo: `$eq $ne $gt $gte $lt $lte $in $nin
  $exists $regex $options $not`, `$and $or`, точечная нотация. Матчер -
  **sift**. [проверено в шаге 4]
  - **Белый список операторов.** Всё остальное - ошибка: sift умеет `$where`
    и выполнил бы строку как код.
  - Сравнение только со скаляром: `{ a: { $gt: { x: 1 } } }` - ошибка.
  - **Вложенные массивы раскрываются, как в sift:** `{ a: 1 }` находит
    `a: [[1, 2]]`. Mongo так не делает. Важнее, чтобы индекс и матчер видели
    одно и то же.
- **Значения - только то, что переживёт JSON.** `Date`, `NaN`, `Map`,
  классы - ошибка с подсказкой "время храните числом". `undefined` в полях
  отбрасывается. В памяти лежит копия через JSON - ровно то, что прочитается
  после рестарта. [проверено в шаге 4]
- **Порядок значений как в Mongo:** null и отсутствующее < числа < строки <
  объекты < булевы. `{ $gt: 5 }` не захватывает строки. Сортировка по
  массиву - по наименьшему элементу (по возрастанию) или наибольшему (по
  убыванию).
- **Без `sort` - по `_id`.** Последний ключ сортировки всегда `_id` в
  направлении первого: при равных значениях порядок стабилен.
- **Обновления:** `$set $unset $inc $push $pull`.
- **Сортировка и пагинация** [решено, в ядре]: `sort`, `limit` и курсор
  `{ _id: { $gt: last } }` / `{ _id: { $lt: last } }`. Это главный запрос
  чата и любой ленты: "последние 50 сообщений комнаты".
- **`limit` и `sort` доходят до индекса**, а не применяются к готовому
  результату. Замер 02: без этого "последние 50 из 100 тыс. в комнате" -
  ~85 мс и 100 тыс. копий документов на каждый запрос. **Шаг 4: 0.05 мс,
  проверено ровно 50 документов**, следующая страница по курсору - тоже.
  [проверено]
- **Индексы:**
  - по `_id` всегда, упорядоченный;
  - на равенство по объявлению: `Map<value, id[]>`, где список id **хранится
    отсортированным по `_id`**. Новые ULID просто дописываются в конец.
    Поэтому "сообщения комнаты, последние 50" - это хвост одного списка, без
    перебора и без сортировки;
  - **тот же индекс даёт диапазоны и сортировку:** рядом со списками лежат
    все значения поля по порядку. Отдельно объявлять "диапазонный" индекс
    не нужно. 10 самых дешёвых из 20 тыс. товаров - 0.01 мс [проверено];
  - **каждый документ есть в каждом индексе** своей коллекции: нет поля или
    пустой массив - ключ null. Иначе сортировка по индексу теряла бы
    документы без поля;
  - поле-массив: документ под каждым значением. Диапазон с двумя границами
    по такому полю использует только одну (условия проверяются по элементам
    отдельно: `[1, 20]` подходит под `{ $gt: 15, $lt: 5 }`), порядок по
    индексу не используется;
  - индекс только на строку, число, булево (или массив из них). **Индекс на
    поле-объект или дату - ошибка при `defineCollection`**, а не молча
    неработающий индекс.
- **Фильтры и правила по вложенным объектам целиком** (`{ meta: { a: 1 } }`)
  запрещены: сравнение объектов зависит от порядка ключей. По вложенным
  полям - через точку: `{ 'meta.a': 1 }`.
- **Планировщик** простой [проверено в шаге 4]: из условий верхнего уровня и
  `$and` выбрать самый узкий источник (равенство, `$in`, диапазон или все
  документы). Границы курсора по `_id` режут списки двоичным поиском.
  Источник даёт нужный порядок - идти по нему до `limit`. Иначе собрать и
  отсортировать. Сортировка по полю с индексом и `limit` - иногда выгоднее
  идти по индексу сортировки и фильтровать. Остаток фильтра проверяет sift:
  индекс отдаёт только кандидатов. `$or` индексы не использует.
- **`explain(filter, opts)`** - откуда взяли кандидатов, сколько проверено,
  сортировалось ли в памяти. Для тестов и `tail`.
- **Схема `z.object` срезает лишние поля** и подставляет умолчания. Нужны
  лишние поля - `z.looseObject`. Ошибка схемы - не ошибка в `before*`:
  действие может её поймать, транзакция продолжится.
- Агрегации (mingo) [позже].

## 9. Хуки

```
beforeCreate  afterCreate
beforeUpdate  afterUpdate
beforeDelete  afterDelete
```

Плюс `on(event)` для любого события шины, `onRequest` на HTTP-запросе и
`onAuth` на аутентификации.

### before*

- Выполняется **внутри транзакции**, до коммита.
- Может изменить документ или бросить ошибку - это бизнес-логика.
- Его записи входят в ту же транзакцию.
- Контекст: `prev`, `next` / `doc`, `user`, `db`, `origin`, `depth`,
  `signal`. `user` - часть транзакции: его задают запись клиента и действие,
  у сервера и сида - `null`. [`user` проверен в шаге 6a; `origin` - позже]

### after* и on(event)

- Выполняются **после коммита, после освобождения очереди и вне контекста**
  транзакции.
- Их записи - новые транзакции. Поэтому `after*` может обновить тот же
  документ и не зависнуть.
- **Ошибка в `after*` не отменяет сохранённое.** Она пишется в лог и в
  `tail`.
- `after*` может потеряться при падении процесса между коммитом и запуском.
  Поэтому правило:

| Что | Где |
|---|---|
| Можно потерять или пересчитать: счётчик просмотров, лог | `after*` |
| Системные события в сокет (`rooms.updated` и т. п.) | **не `after*`**, а `onCommit` - см. §12 |
| Баланс, остаток товара, число использованных приглашений | **в исходной транзакции** (действие или `before*`) |
| Письма, вебхуки, внешние API | запись в `_scheduled` **внутри транзакции**, выполнение отдельно |

Критерий: можно ли потерять обновление и восстановить значение пересчётом.

**Ловушка:** `setTimeout` и другие отложенные вызовы внутри транзакции
наследуют её контекст. Если такой вызов сработает после коммита и что-то
запишет - получит ошибку "транзакция уже отменена". Отложенная работа -
только через `_scheduled` (§13). [проверено в 02]

### Защита от циклов

- У каждой записи и события есть `depth`. Выше порога - ошибка.
- У каждой операции есть `origin` (`api | action | hook | system | seed |
  migration`). Хук может не реагировать на свои же изменения.

## 10. Действия [проверено в шаге 5]

Явная операция бизнес-логики. Одна функция вместо цепочки "клиент поменял
поле -> хук отреагировал -> другой хук".

```ts
defineAction('acceptInvite', {
  input: z.object({ inviteId: z.string() }),
  handler: async ({ input, user, db, emit, signal }) => {
    const invite = await db.invites.findOne({ _id: input.inviteId, to: user.id })
    if (!invite) throw new ActionError('not_found', 'Приглашение не найдено')
    await db.invites.remove(invite._id)
    await db.rooms.update(invite.roomId, { $push: { participants: user.id } })
  },
})
```

- Действие - это транзакция: всё внутри атомарно.
- `input` проверяется по zod до запуска.
- Клиент вызывает действие через HTTP (`POST /api/actions/:name`) или сокет.
- **Клиент просит выполнить действие, сервер сообщает о факте.** Всё, что
  меняет данные со смыслом "это случилось", идёт через действия.
- **По умолчанию действие требует входа**: `user` в обработчике не `null`,
  без входа - 401 до запуска. `public: true` - для действий без входа
  (например, "сбросить пароль"). [решено, Q8] Ограничение частоты
  вызовов [позже].
- Правила коллекций к записям внутри действия **не применяются**: действие -
  серверный код, оно само проверяет, кто что может. Поэтому `create: false`
  у коллекции значит "только через действия".
- **Порядок запуска** [проверено]: действие найдено -> вход -> `input` ->
  только потом транзакция. Неверный запрос очередь записи не занимает.
- **Нет схемы `input` - нет входных данных.** Клиент что-то прислал - 400.
  Иначе в обработчик попадали бы непроверенные данные.
- **Ответ - только JSON**, проверяется до коммита: вернули `Date` -
  транзакция отменяется, клиенту 500.
- **`emit` без `after`** - событие уходит подписчикам `onCommit` только после
  коммита; упавшее действие событий не шлёт. Действие без записей тоже может
  слать события: они уходят с `tx` последней сохранённой транзакции.
- **`emit` с `after`** - задача в `_scheduled` в той же строке лога (§13).

### Ошибки [решено, Q9]

```ts
throw new ActionError('not_found', 'Комната не найдена')
```

| Код | HTTP |
|---|---|
| `bad_request` | 400. Ошибки zod в `input` - тоже 400, с подробностями по полям |
| `unauthorized` | 401 |
| `forbidden` | 403 |
| `not_found` | 404 |
| `conflict` | 409 |
| `invalid_credentials` | 401. Неверный пароль или код [шаг 6b] |
| `too_many_requests` | 429. Лимит попыток входа [шаг 6b] |
| `unavailable` | 503. Внешний сервис не ответил: authphone.su [шаг 6b] |
| любое другое исключение | 500, наружу без подробностей, подробности - в `tail` |

Ошибка схемы коллекции внутри действия - тоже 500: данные клиента проверяет
`input`, а упавшая схема коллекции - ошибка в коде действия. [проверено в
шаге 5]

Любая ошибка отменяет транзакцию. На клиенте - `MabaseError` с тем же
`code`. Эти же коды отдают REST-эндпоинты коллекций (§17).

### Большие удаления [решено, Q12]

Удалить комнату со 100 тыс. сообщений одной транзакцией - это строка лога
~25 МБ и заметное время с занятой очередью записи всей базы. Резать
`removeMany` на пачки нельзя: при падении посередине останется полкомнаты.

Правильный путь - **мягкое удаление**:

1. Действие атомарно помечает родителя: `{ $set: { deletedAt: now } }` и
   ставит отложенную задачу дочистки (§13) - в той же транзакции.
2. Правила сразу перестают показывать и родителя, и его детей (фильтр
   `deletedAt: { $exists: false }`, для детей - через `dependsOn`, §11).
3. Задача удаляет детей пачками по 1000, каждая пачка - своя транзакция. В
   конце удаляет родителя. Упала посередине - повторится (минимум один раз).

`removeMany` одной транзакцией остаётся для небольших наборов. Размер
транзакции в `tail` виден, и выше порога (например, 10 тыс. операций)
`tail` пишет предупреждение.

## 11. Авторизация и правила доступа

### Пользователи [решено]

- `users` - обычная коллекция с зарезервированными полями: `email`,
  `phone`, `passwordHash`, `verified`, `roles`. [проверено в шаге 6b]
- Пароль + JWT с коротким сроком + refresh-токен в системной коллекции.
  Хэш пароля - `Bun.password` (argon2id), без зависимостей. Как именно -
  ниже, "Сессии и токены".
- **Вход по телефону через authphone.su** [решено, мой проект] - см. ниже.
- **Вход через Google и GitHub (OAuth2)** [проверено в шаге 6d] - как в
  PocketBase, см. ниже.
- **Почта** (подтверждение email, сброс пароля, смена email) [проверено в
  шаге 6c] - см. ниже.
- **Расширение `users`:** `defineCollection('users', ...)` в конфиге
  дополняет встроенную коллекцию. Схема расширяется своими полями
  (зарезервированные поля в ней объявлять нельзя - ошибка при старте).
  Правила **заменяются** целиком. По умолчанию, без своих правил: каждый
  видит и правит только себя.

### Сессии и токены [проверено в шаге 6b]

- **email и телефон уникальны и приводятся к одному виду в хуке `users`**:
  на любую запись - клиент, действие, сид. Отдельного уникального индекса в
  ядре нет, хватает хука: он видит записи своей транзакции.
- **access** - JWT HS256 на 15 минут: `{ sub, sid }`. Проверка смотрит, что
  сессия `sid` и пользователь ещё есть. Чистый JWT без этой проверки жил бы
  ещё 15 минут после выхода и смены пароля. В памяти проверка - два поиска
  по `_id`, почти бесплатно.
- **refresh** - `<id сессии>.<случайные 32 байта>`, в `_authTokens` только
  sha256, 30 дней от последнего обновления. **Каждое обновление выдаёт
  новый токен.** Прошлый токен в первые 30 с - 409 (другая вкладка успела
  первой, SDK берёт новый токен из хранилища). Позже - токен утёк, сессия
  закрывается целиком.
- Смена пароля закрывает все сессии. Удаление пользователя удаляет его
  сессии в той же транзакции.
- **Хэш пароля считается до транзакции и не больше двух сразу**
  (`hashConcurrency`): каждый argon2id - 64 МБ, 64 одновременных входа без
  ограничения подняли память до 700 МБ (замер 6b).
- **Лимит попыток:** 10 неудач за 15 минут на email (телефон) + IP - 429.
  Неверный пароль и неизвестный email - одна ошибка и то же время ответа.
- **`signup: false`** закрывает регистрацию для всех способов входа. Сервер
  создаёт пользователей сам (`auth.upsertUser` в сиде, действия).
- Секрет подписи - не короче 32 символов: `MABASE_SECRET`, а если её
  нет - `mb_data/secret.key` (создаётся сам, права 0600). Без файла каждый
  рестарт выкидывал бы всех пользователей. [решено в шаге 7]

### Вход через Google и GitHub [проверено в шаге 6d, на поддельных провайдерах]

Как в PocketBase: провайдер включается строкой в конфиге, ключи - из
переменных окружения.

```ts
auth: {
  providers: ['password', 'authphone', 'google', 'github'],
  oauth: {
    google: { clientId: env.GOOGLE_ID, clientSecret: env.GOOGLE_SECRET },
    github: { clientId: env.GITHUB_ID, clientSecret: env.GITHUB_SECRET },
  },
  appUrl: 'https://chat.example.test', // куда вернуть пользователя
}
```

Поток (authorization code + PKCE, код меняет сервер):

1. SDK создаёт свой `verifier` и открывает
   `/api/auth/oauth/google/start?challenge=<sha256(verifier)>&returnTo=/rooms`.
   Сервер создаёт `state` и **свой** PKCE-ключ (в памяти, 10 минут) и
   отправляет пользователя к Google.
2. Google возвращает на `/api/auth/oauth/google/callback?code&state`.
   Сервер сверяет `state` (одноразовый, того же провайдера), сам меняет
   `code` на токен (с секретом и PKCE-ключом) и читает профиль: id, email,
   подтверждён ли email, имя, аватар. У GitHub email - основной из
   `/user/emails`, а не из профиля.
3. Кто это:
   - есть запись `_externalAuths { provider, providerId }` - этот
     пользователь;
   - вход начат вошедшим пользователем - привязать провайдера к нему (чужой
     аккаунт провайдера - `already_linked`);
   - email у провайдера **подтверждён** и такой пользователь есть -
     привязать к нему (как в PocketBase). **Если его email не был
     подтверждён - пароль стирается, сессии закрываются**: это защита от
     захвата заранее, когда кто-то регистрирует паролем чужой адрес и ждёт
     владельца;
   - email **не подтверждён**, но такой пользователь есть - ошибка
     `email_taken`: войдите паролем и привяжите провайдера в профиле;
   - нет - создать пользователя (если `signup` не выключен). Неподтверждённый
     email в него не пишется: чужой адрес так не занять. Поля из профиля -
     `oauthFields(profile)`, по умолчанию `{ name }`.
4. Сервер возвращает браузер на `appUrl + returnTo` с **одноразовым кодом**
   в `#mb_oauth=...` (не в query: не попадёт в логи сервера и в Referer)
   или с `#mb_oauth_error=<причина>`. SDK меняет код **вместе со своим
   `verifier`** на токены: код из адреса без `verifier` бесполезен. Код
   живёт минуту и сгорает после первой попытки, даже неудачной. Токены в
   адресной строке не появляются никогда.

- `returnTo` - только путь на `appUrl` (`/...`, не `//...`): открытого
  редиректа нет.
- Причины ошибок: `denied` (пользователь отказался), `invalid_state`,
  `provider_error` (обмен кода или профиль не удались; подробности - в
  журнал), `signup_closed`, `email_taken`, `already_linked`.
- Отвязать провайдера можно, если останется другой способ входа: пароль,
  телефон или ещё один провайдер. Удаление пользователя удаляет его
  привязки.

Провайдер - маленькое описание `{ authUrl, tokenUrl, scopes, profile() }`.
Google и GitHub встроены. Яндекс, VK, Apple - тем же способом, когда
понадобятся. [позже]

### Почта [проверено в шаге 6c]

Без почты вход по паролю неполный: нечем прислать сброс пароля и
подтверждение email.

```ts
mail: {
  from: 'Чат <no-reply@chat.example.test>',
  smtp: { host: env.SMTP_HOST, port: 587, user: env.SMTP_USER, pass: env.SMTP_PASS },
  // или своя отправка - для HTTP-сервисов (Resend, Unisender, Postmark):
  // send: async (msg) => { await fetch(...) },
  templates: { resetPassword: ({ user, link }) => ({ subject: '...', text: '...' }) },
}
```

- **Нет `smtp` и `send` - режим разработки:** письма печатаются в консоль
  (в `tail` - на шаге 8), со ссылками. Ничего настраивать для локальной
  работы не надо. Без `appUrl` ссылка в консоли - просто путь.
- **С настоящей почтой `appUrl` обязателен** - ошибка при старте, иначе
  ссылки в письмах никуда не ведут.
- SMTP-клиент - nodemailer 10.1.0 (MIT-0, без зависимостей). **В бинарнике
  работает**, добавляет 0.4 МБ (проверено в 6c на поддельном SMTP-сервере).
  С паролем SMTP без TLS не соединяется (`requireTLS`).
- Встроенные письма: подтверждение email, сброс пароля, смена email. У
  каждого есть шаблон по умолчанию (на русском), любой можно заменить.
- **Ссылки** ведут на страницы фронтенда: `${appUrl}/verify-email`,
  `/reset-password`, `/confirm-email` с `?token=...`. Токен - 32 случайных
  байта; в `_authTokens` хранится только хэш, срок (сброс - 1 час,
  подтверждение и смена email - 24 часа), одноразовый. Новая ссылка того же
  вида отменяет прошлую. Ссылка на адрес, который у пользователя уже
  другой, не работает.
- **Письмо уходит после коммита**, вне очереди записи. Не ушло - токен
  удаляется, клиент получает 503 и может сразу запросить ещё раз. Одно
  письмо одного вида - не чаще раза в минуту (429).
- **Сброс пароля отвечает сразу и одинаково** для любого email; письмо
  уходит в фоне, ошибки - в журнал. Иначе по ответу или по времени было бы
  видно, есть ли такой пользователь. Сброс закрывает все сессии и считает
  email подтверждённым: письмо дошло.
- **Смена email требует пароль** (если он есть): украденная сессия не
  уведёт аккаунт. Письмо - на новый адрес; после подтверждения все сессии
  закрываются, email - это логин. Вошедший по телефону добавляет email без
  пароля.
- Смена пароля любым способом гасит отправленные ссылки сброса.
- `mail.send()` доступен хукам и действиям: `import { mail } from 'mabase'`
  [проверено в шаге 7b]. Из действия - лучше через отложенное событие
  (§13), чтобы не держать очередь и не потерять письмо при падении.
- Секреты - только из переменных окружения, не в `mabase.config.ts`.

### Вход по телефону: authphone.su [решено, детали - §20]

[authphone.su](https://authphone.su) - мой проект: бесплатное подтверждение
номера через Telegram и MAX, без SMS. Пользователь открывает бота,
делится контактом, бот присылает 6-значный код на 3 минуты, код вводится на
сайте.

API сейчас (по сайту, 2026-10-29):

- `POST /generate-code { phoneNumber }` - запросить код. Лимит: 5 запросов
  с одного IP за 3 минуты;
- `POST /auth { phoneNumber, code }` -> `{ status: 'ok', message: 'success' }`.
  Код одноразовый, до 5 неверных попыток.

Как встраивается в MaBase:

```ts
auth: { providers: ['password', 'authphone'] }
```

1. **Код запрашивает браузер** (`mb.auth.phone.start(phone)` в SDK идёт
   прямо в authphone.su). Если запрашивать с сервера, лимит "5 запросов с
   IP за 3 минуты" станет общим на всех пользователей.
2. **Проверяет сервер:** `mb.auth.phone.verify(phone, code)` ->
   `POST /api/auth/phone` -> MaBase сам вызывает `authphone.su/auth`. Только
   ответ сервера authphone, полученный самим MaBase, создаёт сессию. Ответу
   из браузера не верим.
3. Нашёлся пользователь с этим `phone` - вход. Нет - создать (если
   `signup` не выключен). Дальше те же JWT + refresh, что у пароля.
   [проверено в шаге 6b, на подделке authphone]
4. У `users` появляется зарезервированное поле `phone` (E.164, `+79991234567`,
   уникальное, `private` по умолчанию). Номер нормализует MaBase, а не
   пользователь: в примерах authphone номер то с `+`, то без.
5. **authphone не отвечает** (сеть, таймаут 5 с, 5xx, не JSON) - 503
   `unavailable`, а не "неверный код". Вход паролем при этом работает.
   Резервного канала для телефона нет. [решено в шаге 6b]
6. Номер уходит в `/auth` с `+` (`+79991234567`), как в примере на JS на
   сайте. В описании `/auth` на сайте он без `+` - проверить на живом
   сервисе. [открыто, §20]

Что хочу добавить в сам authphone.su, раз это мой проект (не блокирует
MaBase): ключ сайта для серверных вызовов, подписанный ответ `/auth`, коды
ошибок, лимит по сайту, а не по IP.

### Поля [решено]

В конфиге коллекции - четыре списка:

- `fields.readonly` - клиент не пишет их никогда, ни при создании, ни при
  изменении: `roles`, `verified`, `ownerId`, `authorId`. Менять их могут
  только хуки и действия;
- `fields.immutable` - клиент задаёт при создании, потом только чтение.
  Например, `roomId` у сообщения: указать надо, перенести в другую комнату
  нельзя. [Q3]
- `fields.private` - видит только владелец записи. Например, `email`
  пользователя. Владелец: для `users` - сама запись, для остальных - поле
  из `owner: 'ownerId'` в конфиге коллекции. Нет `owner` - ошибка при
  старте. [Q2]
- `fields.hidden` - никогда не уходят наружу: ни в ответах, ни в событиях,
  ни в сокет. Даже владельцу. Например, `passwordHash`.

`private` и `hidden` действуют и на фильтры от клиента: по полю, которое
клиенту не видно, фильтровать нельзя. **По `private` нельзя фильтровать и
сортировать никому, даже владельцу**: фильтр шёл бы по чужим записям.
`hidden` клиент и не пишет. Поля в списках - только верхнего уровня.
Служебные поля клиент не задаёт. [проверено в шаге 6a]

У встроенной `users`: `passwordHash` - hidden; `email`, `phone` - private и
readonly (меняются через вход); `verified`, `roles` - readonly.

### Правила [решено]

Пять правил на коллекцию: `list`, `view`, `create`, `update`, `delete`.

- **`list` и `view` возвращают Mongo-фильтр** (или `false`). Сервер склеивает
  его с фильтром клиента через `$and`, использует индексы, честно делает
  пагинацию. **Тот же фильтр** проверяется sift-ом для сокет-подписок -
  один механизм на HTTP и realtime.
- **Функция-проверка** - для того, что фильтром не выразить. Она
  дополнительно проверяет каждую запись-кандидата.
- **`update` получает `before` и `after`**, чтобы можно было разрешить
  менять текст, но запретить менять автора.
- Правило может быть `async` и читать базу, например чтобы узнать комнаты
  пользователя. Результат правила **кэшируется в пределах одного HTTP-запроса**
  (или одного пересчёта подписок): `roomIdsOf` не выполняется на каждую
  запись-кандидата.
- **Форма контекста** [решено, пример-чат]:

| Правило | Аргументы |
|---|---|
| `list`, `view` | `(user, { db })` -> фильтр или `false` |
| `create` | `(user, { doc, db })` -> `boolean` |
| `update` | `(user, { before, after, db })` -> `boolean` |
| `delete` | `(user, { before, db })` -> `boolean` |

  Значение `false` вместо функции - "всегда нет". Правила нет - тоже "нет":
  доступ открывается явно. `list`/`view` могут вернуть `true` - "без
  ограничений". [проверено в шаге 6a]
- **Ответы:** отказ без входа - 401, со входом - 403. Одна запись не видна
  по `view` - 404, даже если она есть. Чужое по фильтру в списке - пустой
  список.
- **Запись клиента - одна транзакция с проверкой:** `view`, затем
  `update`/`delete` читают базу в той же транзакции, что и пишут. `after` в
  `update` - после операторов, до хуков.

```ts
rules: {
  list:   async (user, { db }) => user
    ? { roomId: { $in: await roomIdsOf(db, user.id) } }
    : false,
  create: (user) => !!user,
  update: (user, { before, after }) =>
    user?.id === before.authorId && after.authorId === before.authorId,
  delete: (user, { before }) => user?.id === before.authorId,
}
```

### Правило зависит от другой коллекции [решено, Q4 - главный пробел]

Правило `messages.list` - "сообщения комнат, где я участник". Участие
хранится в `rooms.participants`. Владелец выгоняет Боба: меняется `rooms`, а
`messages` не меняется вообще. Подписка перепроверяет правило только когда
меняется сама запись (§12) - значит у Боба в открытом чате продолжат
появляться сообщения комнаты, из которой его выгнали. Через сокет утечёт
то, что закрыто по HTTP. Это не редкость: так устроено почти любое правило
"доступ через членство".

Решение для v1 - **правило объявляет зависимости**:

```ts
rules: {
  dependsOn: ['rooms'],
  list: async (user, { db }) => ({ roomId: { $in: await roomIdsOf(db, user.id) } }),
}
```

- Коммит затронул коллекцию из `dependsOn` -> сервер заново вычисляет
  фильтр правила для **живых подписок** на эту коллекцию.
- Фильтр не изменился - ничего не происходит.
- Изменился - клиенту уходит `reset`, и SDK перечитывает выборку тем же
  механизмом, что при реконнекте (§12). Если после перечитывания выборка
  пустая и `view` родителя отказывает - SDK сообщает `revoked`.
- Пересчёт идёт **после коммита, вне очереди записи**, как отправка
  событий. Цена - пересчёт правил на каждый коммит в `rooms`. Комнаты
  меняются редко, это терпимо.
- **Правило читает другую коллекцию, а `dependsOn` не указан** - сервер
  этого не знает. Поэтому при разработке (`mabase serve --dev`) правило
  запускается под прослушкой: читало коллекции не из `dependsOn` -
  предупреждение в консоли и `tail`. [открыто, §20]

Отвергнуто:

- точные `added`/`removed` по зависимостям, когда сервер помнит id,
  отправленные каждой подписке (merge box, как в Meteor) - экономит
  перечитывание, но дорого по памяти и сложно. [позже, если `reset` станет
  узким местом];
- копировать `participants` в каждое сообщение - переписывать всю комнату на
  каждый `kick`.

### Фильтры от клиента [решено]

Фильтр от клиента - это вопрос к базе, и ответ "есть/нет" тоже даёт
информацию.

- **Клиент может фильтровать только по полям, которые ему видны.** Иначе
  скрытое поле подбирается через `$regex` или двоичным поиском через
  `$gt`/`$lt`.
- **`$regex` от клиента ограничен:** длина, простые шаблоны. Иначе один
  запрос повесит единственный процесс (ReDoS).
- **Лимиты:** максимальный `limit`, ограничение на запросы без индекса.
  Серверный код (хуки, действия) лимитов не имеет.
- **Как сделано** [проверено в шаге 6a]: `limit` по умолчанию 100, максимум
  1000. `$regex` не длиннее 64, без групп, `|` и обратных ссылок, не больше
  двух `*`/`+`. **Запрос проверил больше 20 тыс. документов - 400 "добавьте
  индекс"**: лимит на работу запроса, а не запрет полей без индекса. Узкий
  запрос по индексу с остатком без индекса работает. Все лимиты
  настраиваются.

## 12. События и realtime

### Транспорт

Встроенный WebSocket Bun. Включается флагом `realtime: true`. Выключен -
хуки и шина работают, сокет не поднимается.

### Виды событий

1. **Системные** - генерирует ядро **прямо в `onCommit`**, синхронно после
   применения к памяти. Пока процесс жив, они не теряются. Падение процесса
   рвёт и сокеты, и клиенты догоняют состояние через реконнект:
   - `<collection>.created / updated / deleted` [открыто: имя];
   - `user.online / user.offline` (из presence);
   - `auth.login / auth.logout`;
   - `client.subscribed / unsubscribed`.
2. **Серверные пользовательские** - `emit('order.paid', payload)` из
   действий и хуков. Это факты.
3. **Клиентские эфемерные** - `emit('typing', data)` с клиента. Помечены
   `origin: 'client'`. Это не факты: серверные обработчики не должны
   воспринимать их как "что-то случилось". Для фактов - действия.
   [решено, Q6]:
   - клиент может слать **только** события с `from: 'client'` в конфиге,
     остальные сервер отбрасывает с ошибкой;
   - `input` проверяется zod;
   - поле `from` (кто отправил) в конверт ставит **сервер** - клиентскому
     значению верить нельзя.

### Конверт сообщения [решено]

```json
{
  "event": "rooms.updated",
  "eventId": "1201:2",
  "causeId": "1200:1",
  "tx": 1201,
  "ts": 1730200000123,
  "data": { "_id": "r1" },
  "meta": { "collection": "rooms" }
}
```

`eventId` и `causeId` дают цепочку: запрос -> запись -> хук -> следующее
событие. `depth` останавливает цикл, а `causeId` объясняет, откуда он взялся.

### Конфиг событий

```ts
events: {
  'messages.created': { broadcast: 'rules', payload: 'record' },
  typing: {
    from: 'client',
    input: z.object({ roomId: z.string() }),
    allow: async (user, data, { db }) => (await roomIdsOf(db, user.id)).includes(data.roomId),
    to:    async (data, { db }) => (await db.rooms.findOne({ _id: data.roomId }))?.participants ?? [],
  },
}
```

На каждое событие: включено ли (есть ключ), кому видно, что в пэйлоаде
(`record | diff | функция`).

**Кому видно** [решено, Q5]:

- `broadcast: 'rules'` - по правилам коллекции, для системных событий
  записей;
- `broadcast: 'all' | 'authenticated'` - для действительно общих событий;
- `to: (data, ctx) => userId[]` - список получателей, **считается один раз**
  на событие. Для клиентских событий `allow: (user, data, ctx) => boolean`
  решает, может ли отправитель это слать.

Форма `(viewer, data) => boolean` на каждого подключённого клиента
отвергнута: с `async` и запросом в базу это N запросов на каждое нажатие
клавиши.

### Подписки [решено]

`subscribe('messages', filter)` - фильтр клиента + правило `list`,
проверяется sift-ом.

При изменении записи правило проверяется **на старой и на новой версии**:

| Было видно | Стало видно | Клиент получает |
|---|---|---|
| нет | да | `added` с данными |
| да | да | `updated` с данными |
| да | нет | `removed` **без данных** |

Иначе исключённый участник останется с устаревшими данными.

Это ловит только изменение **самой записи**. Если доступ поменялся из-за
другой коллекции (выгнали из комнаты - меняется `rooms`, а не `messages`),
подписке приходит `reset` через `dependsOn` правила (§11).

### Реконнект [решено, обязателен в v1]

Без него схема не сходится: события могут теряться при разрыве и падении,
значит клиент обязан уметь догнать состояние.

Первая версия - простой и всегда правильный вариант, **перечитать**:

1. Клиент подключается и **сначала** подписывается. События, которые приходят
   дальше, он складывает в буфер.
2. Перечитывает данные подписки через обычный запрос. В ответе сервер
   указывает текущий `tx`.
3. Применяет из буфера только события с `tx` больше полученного.

Догон по номеру `tx` (отдать только пропущенное) - оптимизация [позже]. Она
сложнее, чем кажется: для каждого пропущенного события нужно заново
проверить правила на старой и новой версии записи.

Гарантии доставки нет: источник истины - коллекции.

### Presence

Системная коллекция в памяти `_presence`: `{ userId, connectionId,
connectedAt, meta }`.

- `user.online` - первое соединение пользователя;
- `user.offline` - исчезло последнее (несколько вкладок);
- "кто онлайн" - обычный `find` по `_presence` на сервере.

**Клиент видит presence через живую выборку** `mb.live('_presence', {})`, а
кого он видит - решает обычное правило `list` на `_presence` (например,
"только мои контакты"). Одна механика вместо двух. [решено, Q7]

`user.online` с `broadcast: 'authenticated'` не используем: так каждый
вошедший видит, кто онлайн из **всех**, включая незнакомых. События
`user.online` / `user.offline` остаются для серверных хуков.

### Клиентский SDK (тонкий) [решено по примеру-чату]

- `mb.live(collection, filter, { sort, limit })` - запрос + подписка +
  перечитывание при реконнекте и `reset`. Методы: `subscribe(fn)`,
  `loadMore(n)` (курсор строит сам), `on('reset' | 'revoked')`, `close()`;
- `mb.c.<коллекция>.find / insert / update / remove` - REST с правилами;
- `mb.action(name, input)` - вызов действия;
- `mb.emit(event, data)` - только разрешённые клиентские события;
- `mb.on(event, handler)` - события; `mb.on('connection', fn)` - состояние
  соединения (`online | reconnecting | offline`);
- `mb.auth.login / logout / restore / user`. Токены SDK хранит и обновляет
  сам. Ошибка входа - `invalid_credentials`;
- ошибки - `MabaseError` с `code` (§10).

Типизированный клиент (типы из zod-схем конфига без генерации кода) [позже].

### Чего нет

- Комнат как сущности: комната - это подписка с фильтром `{ roomId }`.
- Гарантии доставки и повторов.

## 13. Отложенные и периодические события [постановка проверена в шаге 5, доставка - шаг 10]

```ts
await db.transaction(async (tx) => {
  await tx.users.update(u._id, { $set: { greeted: true } })
  tx.emit('notify', { to: u._id }, { after: '5s', key: `greet:${u._id}` })
})
```

- Отложенный `emit` внутри транзакции - **часть этой транзакции**: запись в
  `_scheduled` попадает в ту же строку лога. Либо обе записи, либо ни одной.
- **Доставка - минимум один раз.** Обработчик должен быть идемпотентным.
- `key` защищает от дублей при постановке: пока задача с этим ключом лежит
  в `_scheduled`, новая не ставится - ни в той же транзакции, ни в
  следующей. [проверено в шаге 5]
- `_scheduled` - системная коллекция с индексами `key` и `runAt`. Документ:
  `{ event, data, runAt, key?, attempts: 0 }`. Выполненная задача
  удаляется (шаг 10), после этого `key` снова свободен.
- Ошибка обработчика - повтор с паузой, после N попыток - задача помечается
  проваленной и видна в `tail`.
- Пропущенные во время простоя задачи [открыто].
- `schedule('digest.daily', '0 9 * * *')` (cron) [позже].

Формулировку "заменяет cron и очередь задач" не используем, пока контракт
выше не реализован и не проверен.

## 14. Наблюдаемость: tail [решено]

`mabase tail` - живой поток в консоли: событие, `tx`, `eventId`, `causeId`,
пэйлоад, какие хуки сработали, сколько заняли, ошибки `after*`, и **сколько
миллисекунд транзакция держала очередь**. Последнее - лучший способ найти
медленный хук.

Делается **вместе с событиями**, а не в конце: без него цепочки хуков не
отладить.

## 15. Сиды и миграции

- `seed.ts` - обычный скрипт на API ядра (`defineSeed`), идемпотентный
  через `upsert` и `count`. `mabase seed`. Тестовых пользователей сид
  создаёт через `auth.upsertUser` - пароль хэшируется как при регистрации.
  Справочным записям сид даёт своё `_id` (§8).
- **Пакетная запись** [решено]: сид и `mabase import` пишут пачками, например
  по 1000 документов в одной транзакции. Отдельный режим не нужен: это та же
  транзакция, просто большая. Один fsync на пачку вместо одного на документ.
  Если процесс умрёт посреди сида, уже сохранённые пачки останутся, сид надо
  повторить. Поэтому сид должен быть идемпотентным.
- Миграции [позже]: `mb_migrations/YYYYMMDDHHMM-name.ts` с `up(db)`,
  применённые - в `_migrations`, без `down`.

## 17. HTTP API [проверено в шаге 7]

`Bun.serve` напрямую, без Hono: путей мало, обработчик - функция
`Request -> Response`, тесты зовут её без сервера.

| Путь | Что |
|---|---|
| `GET /api/health` | `{ ok: true }` |
| `GET /api/c/:collection` | `?filter=<JSON>&sort=<JSON>&limit=50&fields=a,b` -> `{ items }`; `?count=1` -> `{ count }`. Неизвестный параметр - 400 |
| `POST /api/c/:collection` | создать, ответ - запись |
| `GET/PATCH/DELETE /api/c/:collection/:id` | `PATCH` - операторы (`{ $set: ... }`); `DELETE` - 204 |
| `POST /api/actions/:name` | тело - `input`, ответ - результат действия |
| `/api/auth/*` | `register`, `login`, `phone`, `refresh`, `logout`, `me`, `password`, `verify-email/request|confirm`, `reset-password/request|confirm`, `change-email/request|confirm`, `oauth/:p/start` (POST, ответ `{ url }`), `oauth/:p/callback` (302), `oauth/exchange`, `DELETE oauth/:p` |
| `/api/admin/*` | `compact`, `backup { dir }`, `import/:collection` (NDJSON) |
| остальное | статика фронтенда из `publicDir`; путь без расширения, которого нет, - `index.html` |

- **Коллекции - под `/api/c/`, а не прямо под `/api/`** [решено в шаге
  7]. Иначе коллекция `files` или `auth` в приложении столкнулась бы со
  служебными путями.
- **Ошибки:** тело `{ code, message, details? }`, коды - из §10. Плюс:
  413 (тело больше 1 МБ), 415 (не `application/json`), 405. **Таймаут
  транзакции и база "только чтение" - 503 `unavailable`** [решено в шаге
  7]: сервер не справился сейчас, запрос не плохой. Остальное - 500 без
  подробностей, подробности - в журнал (один раз).
- **Токен есть, но неверный или истёк - 401 везде**, даже где гостю можно:
  SDK обновит токен, а не получит молча "ничего не видно".
- `OAuth start` - POST с токеном (если есть): так привязка из профиля
  знает, кто вошёл. Браузер переходит на `url` из ответа. Адрес колбэка
  строится из `serverUrl` (его надо указать за прокси) или из запроса.
- **CORS** выключен по умолчанию; `cors: ['https://...']` или `'*'`.
  Токены в заголовке, не в cookie: CSRF не страшен.
- **IP клиента** для лимитов - адрес соединения. `trustProxy: true` -
  последний адрес в `X-Forwarded-For` (его дописал свой прокси). Без
  `trustProxy` заголовок игнорируется: подделать его может кто угодно.
- **`/api/admin/*` - только с этой машины и только с токеном** из
  `mb_data/admin.json` (права 0600, новый на каждый старт, вместе с адресом;
  при остановке удаляется). За прокси на
  той же машине все запросы приходят с 127.0.0.1 - одной проверки адреса
  мало. Без токена или не с этой машины - 404.
- **Импорт** (`mabase import`): NDJSON, пачками по 1000 в транзакции, мимо
  правил, хуки работают. Документ с `_id`, который уже есть, пропускается:
  повторный импорт безопасен (без `_id` - продублирует). Ошибка в пачке
  отменяет её; сохранённые пачки остаются.
- `Cache-Control: no-store` на всех ответах API.
- `/api/realtime` - WebSocket, шаг 8. `/api/files/*` [позже].

Замер (сервер и клиент в одном процессе, macOS arm64, fsync включён):
`GET` 50 последних записей с правилом - 8 тыс. запросов в секунду при 50
одновременных; `POST` записи - 770 в секунду (каждая - транзакция с
fsync), 380 в секунду по одной.

## 21. Что изменилось относительно idea.md

| Было в idea.md | Стало | Почему |
|---|---|---|
| Лог на каждую коллекцию | Один общий лог, строка = транзакция | Атомарная запись в несколько коллекций, надёжный планировщик |
| Межколлекционных транзакций нет | Есть, через общий лог и очередь | Нужны самому ядру: запись + задача в `_scheduled` |
| "История, replay хуков, аудит бесплатно" | Истории нет в v1; хуки при восстановлении не запускаются | После компактирования лог обрезается; повтор хуков отправил бы письма заново |
| Fallback на Node SEA | Только Bun | Два рантайма - двойная работа ради ненужного сценария |
| Правила `(user, doc) => boolean` | `list`/`view` - фильтр; функция - дополнительная проверка; `update` с `before`/`after` | Индексы, пагинация, один механизм для HTTP и сокетов |
| - | Скрытые и readonly поля, ограничения фильтров от клиента | Утечка через фильтр, ReDoS |
| - | Общая очередь записи, overlay, таймаут с отменой | Гонки в async-хуках |
| - | `after*` вне транзакции, правило "что можно в after*" | Взаимная блокировка, потеря при падении |
| - | Действия (`defineAction`) | Логика одной функцией; клиент просит, сервер сообщает факт |
| `emit` с клиента - как любое событие | Клиентские события только эфемерные | Клиент не должен объявлять "заказ оплачен" |
| Только `depth` | `eventId`, `causeId`, `tx` | Видно, откуда взялась цепочка |
| `tail` в конце | `tail` вместе с событиями | Без него не отладить цепочки |
| "Заменяет cron и очередь задач" | Контракт: минимум один раз, идемпотентность, `key` | Обещание должно совпадать с механизмом |
| `hooks/` и `migrations/` | `mb_hooks/` и `mb_migrations/`, как в PocketBase | Привычно; рядом с бинарником |
| Ошибка хука при загрузке - не описано | Останавливает запуск | Сервер без части логики опаснее, чем упавший |
| `mabase seed` на работающем сервере - не описано | Только при остановленном: сид пишет в базу напрямую. `backup` и `import` - в обоих случаях | Второй процесс базу не откроет (LOCK); исполнять чужой код через admin не хочу |
| `_id` - не описано | ULID | Порядок создания и курсорная пагинация бесплатно |
| Диапазонные индексы позже, сортировки нет | `sort`/`limit`/курсор и индексы с порядком - в ядре | Главный запрос чата и ленты |
| Схема - не описано, что со старыми данными | Проверка только на записи | Старые документы не должны перестать читаться |
| Таймаут не описан (в обсуждении был 5 с) | 2 с от взятия очереди, очередь берётся при первом обращении к базе | Пока транзакция держит очередь, база не пишет |
| События в сокет из `after*` | Из `onCommit` | Не теряются, пока процесс жив |
| "При реконнекте клиент перечитывает" | Реконнект обязателен в v1: подписка -> буфер -> перечитать -> применить буфер по `tx` | Без него потеря события = устаревшие данные у клиента |
| Сид - по одной записи | Пакетами по транзакции | Один fsync на пачку |
| "Универсальная база" | "До сотен тысяч документов на процесс" | Память - жёсткий потолок |
| - | Принцип "действия первыми, хуки вторыми" | Чтобы логика не расползлась по хукам |
| "Один процесс-писатель" - только принцип | Файл `LOCK`, второй процесс получает ошибку | Без замка два процесса тихо теряли половину данных |
| Данные в `mb_data/` | Файлы базы в `mb_data/db/`, хранилище трогает только свои файлы | `types.d.ts` и `files/` лежат рядом |
| Восстановление: "отбросить битое" | Нет `CURRENT` или есть новое поколение с данными - отказ запуска, ничего не удаляется | Молча стереть данные хуже, чем не запуститься |
| Порог компактирования не решён | Когда лог больше снапшота (минимум 16 МБ) | Иначе большая база компактируется постоянно |
| Масштаб в общих словах | ~1 КБ heap на документ, 1 ГБ VPS - 300-400 тыс. | Замер 02 |
| Правило перепроверяется только при изменении записи | `dependsOn` у правила -> `reset` подписки | Выгнанный из комнаты продолжал получать её сообщения (пример-чат, Q4) |
| `broadcast: (viewer, data) => boolean` на каждого клиента | `to` - список получателей один раз, `allow` - может ли отправитель | N запросов к базе на каждое нажатие клавиши |
| Клиент шлёт любое событие | Только объявленные с `from: 'client'`, со схемой; `from` ставит сервер | Иначе любой шлёт что угодно кому угодно |
| `user.online` для всех вошедших | Presence - живая выборка `_presence` с правилом `list` | Незнакомые видели, кто онлайн |
| Поля `readonly` и `hidden` | + `immutable` (задать один раз) и `private` (видит владелец) | `roomId` сообщения, `email` пользователя |
| Действие - любое исключение | `ActionError(code)` с картой на HTTP; по умолчанию нужен вход | Клиенту нужен понятный код, а не 500 |
| Удаление - одна транзакция любого размера | Мягкое удаление + дочистка пачками через `_scheduled` | 100 тыс. сообщений - строка лога 25 МБ и занятая очередь |
| `export` на запущенной базе - не описано | `mabase backup` через admin-эндпоинт сервера | Копировать файлы во время работы небезопасно, второй процесс не откроет базу |
| Диапазонный индекс - отдельный вид | Один индекс поля: равенство, диапазон и сортировка | Меньше понятий; замер шага 4 |
| Матчер sift как есть | sift за белым списком операторов | sift выполняет `$where` как код |
| Значения документа - не описано | Только то, что переживёт JSON; `Date` - ошибка | Иначе после рестарта документ молча другой |
| Вход только по паролю | + телефон через authphone.su (Telegram/MAX) | Мой проект; без SMS |
| OAuth (Google, GitHub) [позже] | В шаге 6, как в PocketBase | Нужно в своих проектах; привычно по PocketBase |
| Почта не описана | SMTP или своя отправка, режим разработки в консоль, встроенные письма | Без неё нет сброса пароля |
| JWT с коротким сроком - и всё | JWT + проверка, что сессия жива; refresh меняется на каждом обновлении | Выход и смена пароля действуют сразу; украденный refresh-токен закрывает сессию |
| `/api/:collection` | `/api/c/:collection` | Коллекция `files` или `auth` столкнулась бы со служебными путями |
| admin-эндпоинт "только с localhost" | localhost **и** токен из `mb_data/admin.json` | За прокси на той же машине все запросы - с 127.0.0.1 |
| OAuth: код в `#`, SDK меняет его на токены | + PKCE и со стороны SDK; привязка по email стирает чужой пароль у неподтверждённого; неподтверждённый email не сохраняется | Код из адреса без `verifier` бесполезен; захват аккаунта заранее |
| Сброс пароля "как обычно" | Ответ сразу и одинаковый, письмо в фоне; смена email - с паролем | По ответу и времени не узнать, есть ли email; украденная сессия не уводит аккаунт |
| Уникальность email - не описано | Хук `users`: нормализация и уникальность на любую запись | Действие или сид иначе создали бы второго пользователя с тем же email |
| Действие: `input` проверяется "до запуска" | До транзакции: вход, `input`, потом очередь; ответ проверяется на JSON до коммита | Неверный запрос не держит базу; ответ, который не отправить, не оставляет записей |

## 23. Черновик API (цель по ощущению)

```ts
// mabase.config.ts
import { ActionError, defineConfig, defineCollection, defineAction, z } from 'mabase'

const rooms = defineCollection('rooms', {
  schema: z.object({
    name: z.string().min(1),
    ownerId: z.string(),
    participants: z.array(z.string()),
  }),
  indexes: ['ownerId'],
  fields: { readonly: ['ownerId', 'participants'] },
  rules: {
    list:   (user) => (user ? { participants: user.id } : false),
    view:   (user) => (user ? { participants: user.id } : false),
    create: (user) => !!user,
    update: (user, { before }) => user?.id === before.ownerId,
    delete: (user, { before }) => user?.id === before.ownerId,
  },
  hooks: {
    beforeCreate: ({ doc, user }) => ({ ...doc, ownerId: user.id, participants: [user.id] }),
  },
})

const messages = defineCollection('messages', {
  schema: z.object({
    text: z.string().min(1),
    roomId: z.string(),
    authorId: z.string(),
  }),
  indexes: ['roomId'],
  fields: { immutable: ['roomId'], readonly: ['authorId'] },
  rules: {
    dependsOn: ['rooms'], // выгнали из комнаты -> подписка перечитается
    list: async (user, { db }) => {
      if (!user) return false
      const my = await db.rooms.find({ participants: user.id }, { fields: ['_id'] })
      return { roomId: { $in: my.map((r) => r._id) } }
    },
    create: (user) => !!user,
    update: (user, { before }) => user?.id === before.authorId,
    delete: (user, { before }) => user?.id === before.authorId,
  },
  hooks: {
    beforeCreate: ({ doc, user }) => ({ ...doc, authorId: user.id }),
  },
})

const invite = defineAction('invite', {
  input: z.object({ roomId: z.string(), userId: z.string() }),
  handler: async ({ input, user, db }) => {
    const room = await db.rooms.findOne({ _id: input.roomId, ownerId: user.id })
    if (!room) throw new ActionError('not_found', 'Комната не найдена')
    await db.rooms.update(room._id, { $push: { participants: input.userId } })
  },
})

export default defineConfig({
  collections: [rooms, messages],
  actions: [invite],
  auth: { providers: ['password'] },
  realtime: true,
  events: {
    'messages.created': { broadcast: 'rules', payload: 'record' },
  },
})
```

```ts
// mb_hooks/welcome.ts
import { on } from 'mabase'

// on() работает как after*: после коммита, вне транзакции
on('user.online', async ({ data, db }) => {
  await db.transaction(async (tx) => {
    const u = await tx.users.findOne({ _id: data.userId })
    if (!u || u.greeted) return
    await tx.users.update(u._id, { $set: { greeted: true } })
    // попадает в ту же транзакцию: либо оба, либо ничего
    tx.emit('notify', { to: u._id, text: 'Привет!' }, { after: '5s', key: `greet:${u._id}` })
  })
})
```
