# MaBase — идея проекта

> Один бинарник. Документная база с Mongo-запросами, хуками, авторизацией и
> событиями «из коробки». Для небольших проектов. MIT.

Этот файл — источник истины по замыслу. Код должен следовать ему; если код
и документ расходятся — сначала правим документ, потом код.

---

## 1. Зачем

Для небольших проектов (пет-проекты, MVP, внутренние инструменты, мобильные
бэкенды) нужен бэкенд, который:

- ставится одним файлом и запускается одной командой;
- не требует SQL, схем и миграций там, где они не нужны;
- даёт авторизацию, права доступа, файлы и realtime без отдельных сервисов;
- позволяет описать бизнес-логику хуками, а не писать «настоящий бэкенд»;
- превращает каждое изменение данных и каждое действие пользователя в
  **событие**, на которое можно повесить обработчик конфигом.

Ближайшие аналоги — PocketBase, Supabase, Meteor, Convex. Ниша MaBase: размер и
простота PocketBase, но на Node/TypeScript, с полноценной событийной моделью и
без облака.

## 2. Принципы

1. **Самое простое из работающего.** Из каждой системы берём одну лучшую идею
   и отбрасываем всё остальное.
2. **Сначала библиотека, потом сервер.** Ядро работает без HTTP — из скриптов,
   тестов, сидов. HTTP и сокеты — слой сверху.
3. **Один язык везде.** Ядро, хуки, сиды, миграции и клиентский SDK —
   TypeScript. Никаких встроенных интерпретаторов.
4. **События — первоклассная сущность**, а не побочный эффект.
5. **Ограничения принимаем осознанно**: один процесс-писатель, база помещается
   в память, нет распределённости.

## 3. Что и откуда берём

| Откуда | Берём | Не берём |
|---|---|---|
| lowdb | ощущение «данные — это просто объект», база как библиотека | один JSON на всё, запись всего файла целиком |
| MongoDB | документ как единица, синтаксис запросов и обновлений | бессхемность без выбора, репликация, шардинг |
| Prisma / Postgres | `seed.ts` как обычный скрипт на своём API, миграции-файлы с таймстемпом | down-миграции, отдельный DSL схем |
| PocketBase | хуки `before*/after*`, правила доступа на коллекцию, файлы как поле, один бинарник | хуки на встроенном JS-движке, admin-UI в первой версии |
| Supabase | пользователь — обычная запись в `users`, JWT + refresh, правила доступа как RLS, realtime | магические ссылки, телефон, MFA, зоопарк провайдеров |
| Redis AOF / NeDB | append-only лог + снапшот | — |
| Meteor / Convex | реактивность «база → фронт», presence | монолит и облако |

## 4. Архитектура — слои

```
cli         → serve / seed / migrate / tail
http        → REST + WebSocket (Hono / Bun)
auth        → коллекция users, JWT, OAuth
events      → шина событий, presence, отложенные и периодические события
hooks       → before*/after* вокруг операций, on(event)
rules       → проверка доступа перед операцией
collections → схема (zod, опционально), find/insert/update/remove, индексы
storage     → append-only лог + снапшот, Map в памяти
```

Каждый слой знает только о нижнем. `storage` + `collections` — отдельный пакет
`@mabase/core`, который не импортирует ничего из верхних слоёв.

## 5. Хранение

- **Формат на диске принимается сразу и не откладывается** — его менять
  больнее всего.
- Папка данных `mb_data/`:
  - `<collection>.log` — append-only JSONL: одна строка = одно событие
    (`record.created / updated / deleted`) с пэйлоадом.
  - `<collection>.snapshot` — полный снимок коллекции на момент времени.
  - Заголовок каждого файла содержит версию формата.
- Старт: читаем снапшот, проигрываем лог поверх. Битая последняя строка лога
  (упали посреди записи) просто отбрасывается.
- Компактирование: по порогу размера лога пишем новый снапшот и обрезаем лог.
- Данные в памяти: `Map<id, Document>` на коллекцию.
- Лог хранит **события, а не команды** — это даёт бесплатно историю изменений,
  replay хуков и аудит (облегчённый event sourcing; источник текущего
  состояния — снапшот + лог, не пересчёт с нуля).
- Системные коллекции начинаются с `_` (`_presence`, `_migrations`,
  `_scheduled`, `_files`). Часть из них in-memory-only.

## 6. Коллекции, схема, запросы

- `defineCollection(name, { schema?, indexes?, rules?, hooks? })`.
- Схема — опциональная, через **zod**: один объект даёт валидацию,
  TS-типы и основу для будущих форм/документации. Нет схемы — свободный
  документ.
- Служебные поля у каждой записи: `_id`, `_createdAt`, `_updatedAt`.
- **Запросы** — подмножество Mongo: `$eq $ne $gt $gte $lt $lte $in $nin $exists
  $regex`, логические `$and $or $not`, точечная нотация. Матчер — **sift**
  (агрегации при необходимости — **mingo**).
- **Обновления**: `$set $unset $inc $push $pull`.
- **Индексы**: по `_id` всегда; по объявлению — равенство (`Map<value,
  Set<id>>`) и диапазон (отсортированная структура, напр. `sorted-btree`).
- Планировщик запроса примитивный: есть индекс под условие → сузить по
  индексу → остаток дофильтровать через sift.
- Транзакции — только внутри одной операции над одной коллекцией.
  Межколлекционных транзакций нет (осознанно).

## 7. Хуки

Жизненный цикл коллекции:

```
beforeCreate  afterCreate
beforeUpdate  afterUpdate
beforeDelete  afterDelete
```

Плюс `onRequest` на HTTP и `onAuth` на аутентификации, плюс `on(event)` для
любого события шины (см. §9).

- `before*` может изменить документ или бросить ошибку — это и есть
  бизнес-логика.
- `after*` — побочные эффекты: письма, счётчики, вебхуки, `emit`.
- Хуки — файлы в `hooks/`, подключаются `import()` при старте. Тот же язык и
  те же типы, что у ядра.
- Контекст хука содержит `origin` (`api | hook | seed | system | migration`),
  `user`, `depth` — см. защиту от циклов в §9.

## 8. Авторизация и правила доступа

- `users` — обычная коллекция с зарезервированными полями
  (`email`, `passwordHash`, `verified`, `roles`).
- Email + пароль из коробки. OAuth — подключаемые провайдеры (на старте
  один-два: Google, GitHub).
- JWT с коротким сроком + refresh-токен в системной коллекции.
- **Правила на коллекцию** — четыре: `list/view`, `create`, `update`,
  `delete`. Каждое — функция `(user, doc) => boolean`. Строковые выражения
  (`user.id == doc.ownerId`) — позже, вместе с admin-UI.
- Те же правила используются для фильтрации сокет-подписок и доступа к
  файлам — через сокет не должно утекать то, что закрыто по HTTP.

## 9. События и realtime — центральная идея

### Транспорт

WebSocket (нужен `close`/ping-pong для presence). Включается флагом
`realtime: true/false`; выключен — хуки и шина работают, сокет не поднимается.

### Два вида событий

1. **Системные** — генерирует ядро, список фиксирован, пользователь только
   включает и настраивает:
   - `record.created / updated / deleted` на коллекцию (из `after*`);
   - `user.online / user.offline` (из presence);
   - `auth.login / auth.logout`;
   - `client.subscribed / unsubscribed`.
2. **Пользовательские** — произвольный `emit('order.paid', payload)` из хуков
   или с клиента. Ядро только маршрутизирует.

### Presence

Системная in-memory коллекция `_presence`: `{ userId, connectionId,
connectedAt, meta }`. Запись создаётся при подключении с валидным токеном,
удаляется при отключении.

- `user.online` = `afterCreate` на `_presence`, когда это первое соединение
  пользователя;
- `user.offline` = `afterDelete`, когда исчезло последнее (несколько вкладок);
- «кто онлайн» — обычный `find` по `_presence`.

### Конфиг событий

```ts
events: {
  'user.online': {
    broadcast: 'authenticated',                 // all | authenticated | (user, data) => boolean
    payload: (p) => ({ userId: p.userId, at: p.connectedAt }),
  },
  'user.offline': { broadcast: 'authenticated' },
  'messages.created': {
    broadcast: (user, record) => record.participants.includes(user.id),
    payload: 'record',                          // запись целиком | 'diff' | функция
  },
}
```

Три решения на событие: включено ли (есть ключ), кому видно, что в пэйлоаде.

### Конверт сообщения

```json
{ "event": "user.online", "ts": 1730200000, "data": { "userId": "u1" }, "meta": { "collection": "_presence" } }
```

### Серверная сторона

`on('user.online', ({ data, user }) => …)` — так же, как `afterCreate`.
Из обработчика можно `emit` следующее событие — цепочки.

### Клиентский SDK (тонкий)

- `subscribe('messages', filter)` — фильтр в Mongo-синтаксисе, проверяется на
  сервере тем же sift;
- `on('user.online', handler)`;
- `emit('typing', data)`.

### Отложенные и периодические события

- `emit('cart.abandoned', payload, { after: '15m' })`;
- `schedule('digest.daily', '0 9 * * *', payload)`.

Персист в `_scheduled`, чтобы пережить рестарт. Это заменяет отдельный cron и
очередь задач.

### Защита от циклов (обязательно)

- У каждого события есть `depth`; после порога (по умолчанию 10) — ошибка.
- У каждой операции есть `origin`; хук может не реагировать на изменения,
  которые инициировал сам.

### Наблюдаемость

`mabase tail` — живой поток событий в консоли: событие, пэйлоад, какие хуки
сработали, сколько заняли. Небольшой кусок кода, но именно он делает систему
понятной, когда цепочек становится много.

### Чего намеренно нет

- Комнат как сущности — комната это подписка с фильтром `{ roomId }`.
- Гарантии доставки и повторов — сокет для «живых» уведомлений, источник
  истины в коллекциях, при реконнекте клиент перечитывает.

## 10. Сиды и миграции

- `seed.ts` — обычный скрипт на API ядра, идемпотентный через `upsert`.
  Команда `mabase seed`.
- Миграции нужны редко (нет `ALTER TABLE`), но «переименовать поле у всех»
  бывает. Папка `migrations/`, файл `YYYYMMDDHHMM-name.ts` с функцией
  `up(db)`. Применённые — в `_migrations`. Без `down`.

## 11. Файлы

- Поле типа `file` в схеме коллекции.
- Хранение в `mb_data/files/<collection>/<recordId>/`.
- Раздача по URL через проверку правил `view` на родительскую запись.
- S3-адаптер — позже, по необходимости.

## 12. HTTP API

- Hono (или нативный Bun-сервер).
- `GET/POST /api/:collection`, `GET/PATCH/DELETE /api/:collection/:id`,
  фильтр в query в Mongo-синтаксисе (JSON).
- `/api/auth/*` — register, login, refresh, oauth.
- `/api/realtime` — WebSocket.
- `/api/files/*` — раздача файлов.
- Статика фронтенда из бинарника (`embed`).

## 13. CLI и сборка

- `mabase serve | seed | migrate | tail | export | import`.
- Рантайм — **Bun**: нативный WebSocket с pub/sub, `bun build --compile` в
  один бинарник. Fallback — Node SEA. Все зависимости чистый JS, без нативных
  модулей — упаковка без сюрпризов.
- Структура проекта пользователя:

```
my-project/
  mabase.config.ts     # коллекции, события, auth
  hooks/
  migrations/
  seed.ts
  mb_data/             # создаётся автоматически
```

## 14. Чего не делаем (сейчас или вообще)

- Admin-UI — не в первой версии; заменяется сидами и REST-клиентом.
- Горизонтальное масштабирование, репликация — вообще.
- Межколлекционные транзакции — вообще.
- Базы, не помещающиеся в память, — вообще (это цена простоты).
- Магические ссылки, SMS, MFA — не в первой версии.

## 15. Порядок разработки

1. `storage` — лог, снапшот, компактирование, восстановление после падения.
2. `collections` — Map в памяти, find/insert/update/remove, sift, индексы.
3. `hooks` — before/after, origin, depth.
4. `auth` + `rules`.
5. `http` — REST.
6. `events` — шина, WebSocket, presence, конфиг событий, конверт.
7. `seed` + `migrate`.
8. Отложенные/периодические события, `tail`.
9. Файлы.
10. Клиентский SDK.
11. Admin-UI — когда всё остальное стабилизируется.

На каждом шаге: тесты на уровне ядра без HTTP.

## 17. Черновик API (цель по ощущению)

```ts
import { defineConfig, defineCollection } from 'mabase'
import { z } from 'zod'

const messages = defineCollection('messages', {
  schema: z.object({
    text: z.string().min(1),
    roomId: z.string(),
    authorId: z.string(),
  }),
  indexes: ['roomId'],
  rules: {
    list:   (user, doc) => !!user,
    create: (user)      => !!user,
    update: (user, doc) => user?.id === doc.authorId,
    delete: (user, doc) => user?.id === doc.authorId,
  },
  hooks: {
    beforeCreate: ({ doc, user }) => ({ ...doc, authorId: user.id }),
  },
})

export default defineConfig({
  collections: [messages],
  auth: { providers: ['password', 'github'] },
  realtime: true,
  events: {
    'user.online':      { broadcast: 'authenticated' },
    'messages.created': {
      broadcast: (user, rec) => !!user,
      payload: 'record',
    },
  },
})
```

```ts
// hooks/welcome.ts
import { on, emit } from 'mabase'

on('user.online', async ({ data, db }) => {
  const u = await db.users.findOne({ _id: data.userId })
  if (!u.greeted) {
    await db.users.update(u._id, { $set: { greeted: true } })
    emit('notify', { to: u._id, text: 'Привет!' }, { after: '5s' })
  }
})
```

## 18. Открытые вопросы

- Имя пакета и бинарника: `mabase`? Проверить свободно ли на npm.
- Hono vs нативный Bun-сервер — решить после прототипа сокетов.
- Формат `diff` в пэйлоаде `record.updated` — только изменённые поля или
  старое + новое.
- Нужен ли `origin`-фильтр в конфиге событий или достаточно его в контексте
  хука.
- Порог компактирования лога — по размеру или по числу записей.

## Как использовать этот файл

При старте работы над кодом: прикрепить `idea.md` и сказать, какой пункт из

  сначала сказать об этом, а не делать молча;
- формат хранения из §5 считать зафиксированным;
- на каждый слой — тесты без HTTP;
- если по ходу принимается новое архитектурное решение — предложить правку
  в этот файл, а не оставлять его только в коде;
- код — TypeScript, Bun, чистый JS в зависимостях, комментарии и README на
  русском, идентификаторы на английском.
